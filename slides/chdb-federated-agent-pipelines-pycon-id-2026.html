A Question Your Agent Can't Answer

“Which of today's support tickets come from our biggest customers?”

Orders

Parquet files in the data lake on S3. Nobody loads them anywhere; they just accumulate.

Customers

A CSV somebody exported from the CRM last week. It lives in a shared folder.

Today's tickets

A JSON response from the support API, currently sitting in a pandas DataFrame.

The model is not the bottleneck.
The answer lives in three places, and the agent can query none of them.
Open with the pain. A completely ordinary business question, and the data layout everyone actually has: a lake, an export, an API. No exotic infrastructure in the story on purpose.

The ETL Reflex — and Why Agents Break It

ETL: Extract data out, Transform its shape, Load it into a warehouse. Then query the warehouse.

ETL was built for dashboards

Questions are known in advance. A nightly refresh is fine. A pipeline per question pays for itself — you will run it for years.

Agents invert every assumption

Questions are unpredictable. The answer is needed in seconds. Most agent questions are asked once — the pipeline never pays for itself.

You can't pre-build a pipeline for a question nobody has asked yet.
Define ETL in one line for people who have never run one. Concede that ETL is the right tool for BI — the argument is only that agents violate its assumptions: known questions, batch latency, reuse.

The Whole Talk in One Query

“Which of today's tickets come from our biggest customers?”


SELECT u.name, u.tier, t.subject, sum(o.amount) AS lifetime_spend
FROM Python(tickets)         AS t   -- API result, in memory
JOIN file('users.csv')       AS u   -- someone's CRM export
  ON u.user_id = t.user_id
JOIN file('orders.parquet')  AS o   -- data-lake extract
  ON o.user_id = t.user_id
GROUP BY u.name, u.tier, t.subject
ORDER BY lifetime_spend DESC

  • LLMs already speak SQL. It's the best-represented query language in their training data.
  • One tool replaces N connectors. Expose run_sql(query); federation handles where the data lives.
  • Every answer is auditable. The generated SQL is the log of exactly what was read.
This is what "agent data pipeline" means here: generated at ask-time, executed in place, thrown away after. One SQL tool beats a zoo of bespoke retrieval functions — fewer tools, better tool-calling accuracy.

-- when a remote path gets hot, cache it — once:
CREATE TABLE hot_orders ENGINE = MergeTree ORDER BY tuple()
AS SELECT * FROM s3('https://…/orders/*.parquet');
ETL didn't disappear. It shrank to one line of SQL, applied only where the profile says it's worth it.
Real numbers from prep, measured on this deck's demo. Column pruning and filter pushdown soften remote scans, but a full scan still moves bytes. The pattern: federate first, measure, materialize the hot paths. That is "federated by default" — not "federated always".

Three Takeaways

  1. Agents ask unpredictable questions. Pipelines built in advance answer yesterday's questions. Query data where it lives.
  2. One SQL surface is the agent's data tool. Files, lakes, live databases, DataFrames — chDB federates them inside your Python process.
  3. Materialize only what gets hot. ETL becomes a one-line optimization, not a prerequisite.
