Porting a C++ Python extension to free-threaded Python 3.14

Auxten Wang · Technical Director @ ClickHouse · Creator of chDB

One story. What it took to make a C++ extension faster on free-threaded Python, and what we measured at the end. The workload that hurt us was many concurrent queries from one Python process, most of them coming out of our own agent tool loops. The GIL sat in the middle of every one of them. Every core, one process, no worker pool: that is the target. Numbers at the end.

Part 1
01

Why free-threaded Python matters for native extensions

Part one. Why we bothered, what changed in 3.14, and why your extension does not benefit automatically. 3.14t runs Python on every core; your C extension does not get that for free.
Why

The engine had every core. Python had one lane.

Agent tool loops, pandas services: many queries at once, one interpreter.

A chatbot is one request. An agent is a loop: plan, call a tool, read, call another tool, and most of those calls are data access: filter and rank a memory table, join S3 with Postgres and a DataFrame in one SQL, call a Python function per row, hand a DataFrame back. Every one of them touches Python. We had already put the data layer in-process for latency, so that one process has to use the whole machine. The engine could. Python let one thread through at a time. If you never touch an agent: a service that runs many pandas jobs from one process has exactly the same lock in the middle.

Thirty seconds of history, because it explains the tax. 1996: Greg Stein removed the GIL from Python 1.4 with fine-grained locks. It worked, and single-threaded code got much slower, so it died. 2009: Antoine Pitrou rewrote the GIL for 3.2. Fairer scheduling, same lock. 2016: Larry Hastings' Gilectomy. Every refcount became an atomic operation and the interpreter crawled; abandoned. 2017 onwards: Eric Snow gave each sub-interpreter its own GIL, landed in 3.12. A sidestep, not a removal. 2021: Sam Gross's nogil fork solved the refcount problem with biased reference counting and immortal objects, kept single-thread speed within a few percent, and became PEP 703. Every failure was the same failure: single-thread speed. That is why the small remaining tax on the next slide matters.
3.14t

What landed in 3.14t

PEP 703 → PEP 779: supported, not experimental
python3.14t — the t is for threads
~1–8% single-thread cost
Deliberately one slide. PEP 703 made the GIL optional in 3.13 as an experiment; PEP 779 made it supported in 3.14. It is a separate interpreter, python3.14t, and a separate wheel tag. The single-thread penalty came down from roughly 40 percent in 3.13t to a few percent. That made it usable. Most of the top compiled packages now ship free-threaded wheels. Under the hood: biased refcounting, immortal objects, per-object locks. That is why it is fast. It is also why a borrowed reference that was harmless for thirty years can now be a use-after-free when another thread mutates the container.
The catch

Your extension gets nothing for free

One undeclared import: GIL back on
"Thread-safe because GIL" is a race
No stable ABI. New wheels, new CI.
Three things bite. First, the silent re-enable: import one extension that has not declared itself safe and CPython turns the GIL back on for the whole process, with a warning most people never read; the warning names the module. Second, twenty years of code that was thread-safe only because the GIL serialized it. Third, the stable ABI, the one-wheel-fits-many-Pythons shortcut, does not exist on the free-threaded build; you build and ship a separate wheel. The consequence: a process running concurrent queries on 3.14t got zero benefit, because our module was the one that had not opted in. Fixing that is the rest of the talk.

Where our embedded engine still hit the GIL

Part two: where exactly the lock was. The engine was already parallel; every call into Python was not. One slide to introduce the patient, then the three places every engine thread had to queue.
chDB

chDB: the ClickHouse engine inside your Python process

pip install chdb

sess = chdb.session.Session("./brain")
sess.query("""
  SELECT m.text FROM memory m
  JOIN s3('s3://lake/events/*.parquet') e USING (user_id)
  JOIN Python(tickets) t USING (user_id)
  WHERE m.user_id = 'u1' LIMIT 8""")
For those who do not know ClickHouse: it is the open-source columnar analytics database. chDB is that whole engine as a pip install, living inside your Python process, no server. Local tables on disk, files on S3, a Postgres table, a live DataFrame: all tables in one statement. You do not need any ClickHouse knowledge for the rest of the talk. What matters: the engine is heavily multi-threaded C++, glued to Python by pybind11, and it touches Python in exactly three places: UDFs, DataFrames in and out, and strings. Those three places are the whole story.
Three doors

Parallel engine, serial glue

UDF calls

Every engine thread, one lock.

String columns

One Python object per cell.

DataFrames

Every frame crosses the lock.

Three doors, one lock on each. A UDF is your Python function called from SQL, per row; on a stock build the engine threads take turns at the interpreter. Strings: agent memory is text all the way down, and a pandas object column of text is one Python object per cell, a refcounted heap object, each one read under the lock. And the DataFrame path, which matters most to this room: every frame that goes in or comes out is a long series of tiny Python calls, NULL checks, dtype lookups. The engine was never the bottleneck. The lock was: it serialized every conversation with Python.
Part 3
03

Three changes that unlocked parallelism

Two prerequisites. One GIL change.

The meat. Three changes in the order we made them: run Python UDFs in-process, declare the module GIL-independent, rework the string hot paths. Be clear about what they are: only the second one is about the GIL. The first is a prerequisite, restructuring so that free-threading has something to speed up. The third is mostly about avoiding Python objects, and the biggest number in it has nothing to do with the GIL; it works on stock Python too. I will say so again when we get there.
Change 1

Free-threading cannot speed up a fork()

A fresh interpreter per query
Rows piped as text
Your model, loaded again per fork
Change one starts with an embarrassing admission. Our Python UDFs did not run in the process at all. The decorator generated a script and a config file, the engine forked a fresh interpreter, and rows went through as tab-separated text. For a scoring or embedding function this was fatal: the model you had already loaded was not there. It got loaded again, inside the fork, per query. Free-threading would have done nothing for this design: there was no Python in our process to parallelize. The bottleneck was fork, not the GIL. Step one was a prerequisite.
Change 1

In-process UDFs: now there is something to unlock

from chdb import func
from chdb.sqltypes import STRING, FLOAT64

@func([STRING, STRING], FLOAT64)
def score(text, q):
    return reranker(text, q)  # loaded once

sess.query("SELECT text, score(text, 'S3 cost') AS s "
           "FROM memory ORDER BY s DESC LIMIT 8")
After: the decorator registers a real Python callable and the engine's worker threads call it with typed arguments. The example is a reranker scoring rows against the current question, using the model the process already has. No fork, no text protocol. Under the hood, each engine worker thread takes a gil_scoped_acquire before the call. Correct, necessary, and on a stock interpreter that acquire is the lock: every worker thread reaches that line and waits its turn. We moved Python execution into the process precisely so that free-threading would have something to work on. Next slide is what happened when it did.
Change 1

Same UDF, 8 threads: 0.85 s → 0.15 s

Stock 3.14 is one bike lane: sixteen engine threads, only one of them runs Python at a time, the rest queue. So the stock number barely moves with thread count. One caveat: 0.85 is the contended number, threads handing the lock around, so do not read 0.85 against 0.72 as the single-thread tax; that is a different measurement. 3.14t gives every thread its own lane: one thread 0.72 seconds, eight threads 0.15, flat to 32. Same C++, same acquire, but on 3.14t that acquire is per-thread bookkeeping, not a global lock. Setup: a four-million-row scalar UDF, engine threads inside one query, a 16-core box, best of three. Your UDF now runs concurrently, so it has to be thread-safe. A model forward pass usually is. A dict used as a cache is subtler: single operations are atomic on 3.14t, but "if key not in cache, compute and store" still races. And a subprocess pipeline gains nothing from any of this, which is why the order was in-process first, then free-threaded.
Change 2

One line, one promise: nothing here needs the GIL

// pybind11 ≥ 2.13
PYBIND11_MODULE(_chdb, m,
    py::mod_gil_not_used())
Change two is one line; the raw C API has the same slot, Py_mod_gil with Py_MOD_GIL_NOT_USED. The line itself is a promise: nothing in this module relies on the GIL for correctness. Keeping it meant auditing every global: the type cache, the UDF registry, the engine singleton. Each needed a real lock. One detail matters later: CPython's own PyMutex detaches the thread from the interpreter while it waits; a C++ mutex or call_once does not. Remember that for the bug story. Borrowed references, pointers you do not own, became strong ones wherever another thread could mutate the container underneath us. None of it is clever. The GIL was just hiding the to-do list.
Change 2

Our import cache raced for years. The GIL was its alibi.

First NULL → a lazy import
Segfault, far from the bug
Then a hang. No traceback.
The fix for the race was four lines: std::call_once around the cache initialiser, lock-free reads afterwards. This code sits on the scan path, so a global mutex would have serialized every scan thread. Note what the initializer does: it resolves Python types, pandas and numpy. That detail comes back in part four. Then the bug that fixing the race exposed. First NULL in a string column, and a scan thread lazily imports pandas.NaT. On the stock build that path ran under a GIL acquire; our new fast path had dropped it, so the thread was not attached to the interpreter at all. Segfault inside the allocator, nowhere near the cause. Then the fatal-signal handler deadlocks: no traceback, no exit, the query just hangs. The fix was two lines: resolve those attributes eagerly at module init, while the thread is attached. Finding it took days. Free-threading bugs do not crash loudly. They go quiet. Debugging a hang that gives you nothing is the expensive part.
Change 3

Strings: go straight to the bytes

// FillColumnString, free-threaded build
if (PyUnicode_IS_COMPACT_ASCII(obj)) {         // logs, ids, keys
    data = (const char *) PyUnicode_1BYTE_DATA(obj);  // no copy
    len  = PyUnicode_GET_LENGTH(obj);
} else {
    data = PyUnicode_AsUTF8AndSize(obj, &len);  // thread-safe
}
Change three, strings. For a memory table or a log, strings are the payload. Millions of them cross the C++/Python border per query, and every one went through a pybind11 shim and a friendly Unicode API, one call per value. The free-threaded build cannot use the stable ABI at all, which turned out to be a gift: nothing left to lose, so we replaced the wrappers with direct CPython calls. If the string is compact ASCII, which most logs, identifiers and JSON keys are, it is a pointer and a length; no copy. That buffer is immutable, so reading it from any engine thread is safe. Everything else goes through PyUnicode_AsUTF8AndSize, the public call. We first read CPython's cached UTF-8 field directly; that field is filled lazily, and reading it from another thread is a data race on 3.14t. The public call handles that. Low-level where the layout is fixed, public API where it is not.
Change 3

219 s → 20 s. Not the lock: zero-copy.

object dtype
one Python object per row
219.2 s
Arrow-backed
plain buffers, no Python objects
20.1 s

Works on stock Python today.

And then the biggest single win had nothing to do with locks. pandas 3, with PyArrow installed, stores string columns the way Parquet does: a validity bitmap, an offsets array and one contiguous buffer, not a million tiny Python objects. Every engine thread reads it directly, zero-copy, and no thread ever touches a Python object. ClickBench on a 50-million-row DataFrame, 43 queries: 219 seconds down to 20, 10.9 times less total time; the geometric mean across queries is 4.5, and the string-heavy queries gain up to 64 times. This one needs no free-threading. It works on the Python you already have. So the ranking on a hot path: avoid Python objects if the layout lets you; if not, read them as cheaply as CPython allows. Free-threading is for the ones you cannot avoid.
Part 4
04

Three bugs the GIL had been hiding

Crashes hid as hangs
Cold start: garbage-collector deadlock
Past 8 threads: GC storms
Part four. Three bugs, all of them older than the port. Crashes turning into hangs is worse in a service, because a hung call looks like a slow one. The second is the import-cache initializer from part three, on a cold start with 32 threads. It resolves Python types, so it can allocate, so it can trigger a garbage collection. The free-threaded GC stops the world and waits for every attached thread to reach a safe point. The other threads were blocked inside std::call_once, still attached, never reaching one. Everything froze. The fix: detach from the interpreter before you block on a C++ primitive, or use PyMutex, which detaches for you. Third, UDF throughput collapsed past eight threads: one throwaway argument tuple per row kept waking the garbage collector. Reusing the argument frame with Vectorcall fixed it and cut call overhead 4.7 times. We found the last two only by benchmarking. Free-threading did not create these bugs. It revoked the amnesty.
Part 4

Where no-GIL helps

No gain

Work already outside Python
Zero-copy, no Python objects
Single-threaded jobs

Real gain

Threads running Python
Threads reading Python objects
Many callers, one process
Anything that already ran outside the GIL did not get faster: numpy, Polars, pyarrow doing their heavy work in C; our pure-engine query, no Python objects involved, was 0.161 seconds on both builds. Anything we could make zero-copy got faster without free-threading, and got more from that than from the lock going away. And a single-threaded job, one Airflow task, pays the small tax for nothing. Where it paid: many threads running Python or reading Python objects. The scoring function in the query, the object column of tool output, and the case that started all this: many callers in one process, each wanting the engine now. If you keep Python out of the query, stay on stock. If you want Python in the query, this is what makes it scale.
Part 5

Object strings, 16 threads: 0.22 s → 0.08 s

Part five, the number. A scan over five million values, one Python object each, the pattern of a log or transcript column. Two ratios, and I want you to hear both. Against stock's best run, fewer threads, 0.13 seconds: 3.14t at 16 threads is 1.6 times faster. Against stock at the same 16 threads it is 2.6 times, because on stock adding threads made it slower: they pile onto the lock. On 3.14t adding threads made it faster. The control, a query with no Python objects at all, was 0.161 seconds on both builds: same engine, same speed, only the Python touchpoints moved. Setup: 56-vCPU Xeon, CPython 3.14.6 against 3.14.6t, minimum of six runs.
Part 5

Agent queries and pandas jobs, one process

On stock Python

A pandas chain becomes one SQL.

14 of 16 ops faster.

3.14t adds

Many jobs in flight.

1 model in memory.

This is the pattern. One process, one reranker loaded once, a thread pool. An agent tool call with a Python scoring function inline; next to it a pandas chain over Parquet on S3, written against chdb.datastore, the pandas-shaped API, which compiles to one SQL and runs on the engine. That part works on stock Python today: we measured a 10-million-row Parquet against pandas on one laptop, faster on 14 of 16 everyday operations, sorts 35 to 52 times faster, peak memory 1,059 down to 440 megabytes. On stock Python the thread pool is decoration: every path funnels through the GIL. On 3.14t the pool is real. No worker processes, no pickling, one copy of the model. The sketch: recall() is one SQL with a @func score inside, report() is a chdb.datastore chain over Parquet, both submitted to one ThreadPoolExecutor. A sketch, not a benchmark. The numbers were the previous slide.

@chdb.func([INT64], INT64)
def slow(x): return sum(range(x % 500))
chdb.query("SELECT sum(slow(number)) FROM numbers_mt(2e6) "
           "SETTINGS max_threads=8")
The slide to photograph. Install: uv fetches the free-threaded build if you ask for 3.14t; the python.org installer has a checkbox. Check: import your whole stack, then print the flag. False means the GIL is off. If instead you see "RuntimeWarning: The global interpreter lock (GIL) has been enabled to load module 'X', which has not declared that it can run safely without the GIL", one of your packages has not opted in and dragged the GIL back for the whole process; the message names it. PYTHON_GIL=0 or -X gil=0 forces it off, but that hides the warning: check first, force second. The tracker at py-free-threading.github.io/tracking lists which packages are ready. Try: install chdb, import INT64 from chdb.sqltypes, define a small Python function and call it from SQL with eight engine threads. Each thread calls your function per row. On stock they take turns at the lock; on 3.14t they do not. Time it on both builds on your own laptop. Same shape as the bike-lane benchmark: one query, engine threads, a Python function in the middle.
