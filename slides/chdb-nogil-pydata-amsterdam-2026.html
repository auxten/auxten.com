Porting a C++ Python extension to free-threaded Python 3.14

Auxten Wang · Technical Director @ ClickHouse · Creator of chDB

One story. What it took to make a C++ extension faster on free-threaded Python, and what we measured at the end. The workload that hurt us was many concurrent queries from one Python process, most of them coming out of our own agent tool loops. The GIL sat in the middle of every one of them. Every core, one process, no worker pool: that is the target. Numbers at the end.

Part 1 · Why it matters
01

Why free-threaded Python matters for native extensions

3.14t runs Python on every core. Your C extension does not get that for free.

Part one. Why we bothered, what changed in 3.14, and why your extension does not benefit automatically.
Part 1 · The motivation

The engine had every core. Python had one lane.

Our load became an agent's tool loop: many queries at once, one interpreter.

Recall

Filter + rank a memory table.

Federate

S3 + Postgres + a DataFrame. One SQL.

Score in Python

Call a Python function per row.

Hand back a DataFrame

Millions of Python objects.

Same pattern for data engineers: a service running many pandas jobs from one process.

The engine was multi-threaded. The Python process around it was not.
A chatbot is one request. An agent is a loop: plan, call a tool, read, call another tool, and most of those calls are data access. Look at the cards: those are the four things a tool call does, and every one of them touches Python. We had already put the data layer in-process for latency. Once everything runs inside one process, that process has to use the machine. The engine could. Python let one thread through at a time. If you never touch an agent, read the bottom line: a service that runs many pandas jobs from one process has exactly the same lock in the middle.
Part 1 · Python 3.14t

What 3.14t changes

PEP 703 → PEP 779

GIL optional in 3.13. Free-threading supported in 3.14.

A separate download

python3.14t — the t is for threads. ~1–8% single-thread cost.

The ecosystem followed

Most of the top compiled packages ship 3.14t wheels.

$ python3.14t -c "import sys; print(sys._is_gil_enabled())"
False

False: threads now run Python bytecode in parallel.

One slide of context. The rest is engineering.
Deliberately one slide. PEP 703 made the GIL optional in 3.13 as an experiment; PEP 779 made it supported in 3.14. It is a separate interpreter, python3.14t, and a separate wheel tag. The single-thread penalty came down from roughly 40 percent in 3.13t to a few percent. That made it usable. The ecosystem followed: most of the top compiled packages now ship free-threaded wheels, and the community tracker lists the rest. Under the hood: biased refcounting, immortal objects, per-object locks. That is why it is fast. It is also why a borrowed reference that was harmless for thirty years can now be a use-after-free when another thread mutates the container. That is the whole history lesson.
Part 1 · The catch

Your extension gets nothing for free

One extension that has not opted in turns the GIL back on for the whole process.
"Thread-safe because GIL" is now a data race.
No abi3 (one wheel for many Python versions) on 3.14t. New wheels, new CI.
$ python3.14t -c "import _chdb"
RuntimeWarning: The global interpreter lock (GIL) has been enabled to load module
'_chdb', which has not declared that it can run safely without the GIL.
To override, set PYTHON_GIL=0 or -Xgil=0.
Free-threading is opt-in, per extension module. The rest of this talk is what opting in took.
Three things bite. First, the silent re-enable: import one extension that has not declared itself safe and CPython turns the GIL back on for the whole process, with a warning most people never read. Second, twenty years of code that was thread-safe only because the GIL serialized it. Third, the stable ABI does not exist on the free-threaded build, so the one-wheel-fits-all shortcut is gone; you build and ship a separate wheel. The practical consequence: a process running concurrent queries on 3.14t got zero benefit, because our module was the extension that had not opted in. That warning is us. Fixing it is the rest of the talk.

Part 2 · Three doors

Parallel engine, serial glue, serial query

Python UDF calls

score(text, q) per row. Every engine thread, one lock.

String-heavy columns

Chat logs, tool output, JSON: one PyObject (a refcounted heap object) per cell, read under the lock.

DataFrame integration

pandas in, pandas out. Every frame crosses the lock.

The GIL did not slow the engine down. It serialized every conversation with Python.
Look at the picture. Eight engine threads on the left, happily parallel. Three doors on the right, and every door has the same lock. A UDF that scores rows calls back into the interpreter per row; on a stock build the engine threads take turns. Strings: agent memory is text all the way down, and a pandas object column of text is one Python object per cell, each one read under the lock. And the DataFrame path, which matters most to this room: every frame that goes in or comes out is a long series of tiny Python calls, NULL checks, dtype lookups. The engine was never the bottleneck. The lock was.
Part 3 · Three changes
03

Three changes that unlocked parallelism

Only one of the three is a GIL change. The other two were prerequisites, and they work on stock Python too.

01

Run Python UDFs in-process

Prerequisite: give free-threading something to work on

02

Declare the module GIL-independent

The GIL change: one line, and an audit

03

Rework the string hot paths

Mostly zero-copy. Stock Python gets it too

The meat. Three changes in the order we made them. Be clear about what they are: only the second one is about the GIL. The first is a prerequisite, restructuring so that free-threading has something to speed up. The third is mostly about avoiding Python objects, and the biggest number in it has nothing to do with the GIL. I will say so again when we get there.
Change 1 · Prerequisite

Free-threading cannot speed up a fork()

Our UDFs fork()ed a Python interpreter per query
Rows piped as text. Every argument arrived as a string.
Your loaded model? Loaded again, per fork.

The bottleneck was fork(), not the GIL.

Change one starts with an embarrassing admission. Our Python UDFs did not run in the process at all. The decorator generated a script and a config file, the engine forked a fresh interpreter, and rows went through as tab-separated text. For a scoring or embedding function this was fatal: the model you had already loaded was not there. It got loaded again, inside the fork, per query. Free-threading would have done nothing for this design. There was no Python in our process to parallelize. So step one had nothing to do with the GIL. It was a prerequisite.
Change 1 · UDFs

In-process: faster, and now there is something to unlock

from chdb import func
from chdb.sqltypes import STRING, FLOAT64

@func([STRING, STRING], FLOAT64)
def score(text, q):
    return reranker(text, q)  # loaded once

sess.query("""
  SELECT text, score(text, 'S3 cost') AS s
  FROM memory ORDER BY s DESC LIMIT 8""")
// C++: engine worker threads call it
py::gil_scoped_acquire acquire;  // THE lock

for (size_t row = 0; row < rows; ++row)
{
    py::tuple  args = box_arguments(row);
    py::object out  = func(*args);
    insert_into_column(result, out);
}

Faster already. But on a stock build, every engine thread waits its turn at that line.

After: the decorator registers a real Python callable and the engine's worker threads call it with typed arguments. The example is a reranker scoring rows against the current question, using the model the process already has. No fork, no text protocol. On the right, the one line that matters is the acquire. Correct, necessary, and on a stock interpreter it is the lock: every worker thread reaches that line and waits its turn. We moved Python execution into the process precisely so that free-threading would have something to work on. Next slide is what happened when it did.
Change 1 · UDFs

This is what no-GIL was made for

Stock: ~0.85 s, 1 to 32 threads. They take turns.
3.14t: 1 thread 0.72 s → 8 threads 0.15 s. Flat to 32.
Your UDF runs concurrently now. Make it thread-safe.

4M-row scalar UDF, engine threads inside one query, 16-core x86_64, best of 3.

Order matters: in-process first, then go free-threaded.
Amsterdam picture. Stock 3.14 is one bike lane: sixteen engine threads, only one of them runs Python at a time, the rest queue. So the stock number barely moves with thread count. One caveat about reading it: 0.85 is the contended number, threads handing the lock around. We did not isolate a single uncontended stock thread for this function, so do not read 0.85 against 0.72 as the single-thread tax; that tax is real and it is a different measurement. 3.14t gives every thread its own lane. Same C++, same gil_scoped_acquire, but on the free-threaded build that acquire is per-thread bookkeeping, not a global lock. Two more caveats. Your UDF now runs concurrently, so it has to be thread-safe. A model forward pass usually is, if the model library ships free-threaded wheels. A dict you use as a cache is subtler: single operations are atomic on 3.14t, but "if key not in cache, compute and store" still races, and you compute twice. And a subprocess pipeline gains nothing from any of this, which is why the order was in-process first.
Change 2 · Opt in

One line, one promise: nothing here needs the GIL

// pybind11 ≥ 2.13
PYBIND11_MODULE(_chdb, m,
    py::mod_gil_not_used())
// raw C API
{Py_mod_gil, Py_MOD_GIL_NOT_USED},
Every global variable and cache needed a real lock.
Every borrowed reference (a pointer you do not own) became a strong one.
Our import cache had a race for years. The GIL was its alibi.
None of the fixes were exotic. The GIL was just hiding the to-do list.
Change two is one line in two dialects. The line itself is a promise: nothing in this module relies on the GIL for correctness. Keeping that promise meant auditing every global: the cache that resolves pandas and numpy types, the UDF registry, the engine singleton. Each got a lock that fits. One detail matters later: CPython's own PyMutex detaches the thread from the interpreter while it waits; a C++ mutex or call_once does not. Remember that for the bug story. Borrowed references became strong ones wherever another thread could mutate the container underneath us. None of it is clever. The uncomfortable finding was that our import cache's lock-free fast path had been a race for years. The GIL had been covering for it.
Change 2 · Shared state

Fix the race, then the bug it was hiding

// import cache, on the scan path
static std::once_flag init_flag;
std::call_once(init_flag, [] {  // one-shot
    cache = make_shared<ImportCache>();
});   // then lock-free reads

Trigger. First NULL in a string column (every other row in real data) → lazy import of pandas.NaT from a thread Python does not know about.

Crash. Segfault in the allocator, far from the bug.

Hang. Signal handler deadlocks. No traceback. Forever.

Fix: resolve imports eagerly, at module init.

Debugging a hang that gives you nothing is the expensive part.
Left is the fix for the race, four lines. This code sits on the scan path, so a global mutex would have serialized every scan thread. call_once gives a one-shot init and a lock-free read afterwards. Note what the initializer does: it resolves Python types, pandas and numpy. That detail comes back in part four. Right is the bug that fixing the race exposed. First NULL in a string column. A scan thread lazily imports pandas.NaT. On the stock build that path had run under a GIL acquire; our new fast path had dropped it, so the thread was not attached to the interpreter at all. Segfault inside the allocator, nowhere near the cause. Then the fatal-signal handler deadlocks: no traceback, no exit, the query just hangs. In a service that looks like a request that never returns. The fix was two lines: resolve those attributes eagerly at module init, while the thread is attached. Finding it took days. Free-threading bugs do not crash loudly. They go quiet.
Change 3 · Strings

Strings are the hot path: go straight to the bytes

// FillColumnString, free-threaded build
if (PyUnicode_IS_COMPACT_ASCII(obj)) {      // most logs, ids, keys
    data = (const char *) PyUnicode_1BYTE_DATA(obj);   // no copy
    len  = PyUnicode_GET_LENGTH(obj);
} else {
    data = PyUnicode_AsUTF8AndSize(obj, &len);   // public, thread-safe
}
ASCII str → a pointer read. The buffer never changes, so any thread may read it.
Millions of values per query: one shim call per value is one too many.
No stable ABI on 3.14t anyway. Nothing left to lose by going low-level.
Change three, strings. For a memory table or a log, strings are the payload. Millions of them cross the C++/Python border per query, and every one went through a pybind11 shim and a friendly Unicode API, one call per value. The free-threaded build cannot use the stable ABI at all, which turned out to be a gift: we replaced the wrappers with direct CPython calls. If the string is compact ASCII, which most logs, identifiers and JSON keys are, it is a pointer and a length; no copy. That buffer is immutable, so reading it from any engine thread is safe. Everything else goes through PyUnicode_AsUTF8AndSize, the public call. We first read CPython's cached UTF-8 field directly; that field is filled lazily, and reading it from another thread is a data race on 3.14t. The public call handles that. Low-level where the layout is fixed, public API where it is not.
Change 3 · Strings

Then the biggest win turned out not to be the lock at all

pandas 3 (with PyArrow) stores strings the way Parquet does: one buffer, not a million tiny Python objects.

object dtype — 219.2 s
Arrow zero-copy — 20.1 s

10.9× less total time. No GIL involved: this works on stock Python today.

ClickBench, 50M rows, 43 queries · geomean 4.5× · string-heavy up to 64×

Avoid Python objects first. Free-threading is for the ones you cannot avoid.
And then the biggest single win had nothing to do with locks. pandas 3, with PyArrow installed, stores string columns the way Parquet does: a validity bitmap, an offsets array and one contiguous buffer. Plain memory. Every engine thread reads it directly, zero-copy, and no thread ever touches a Python object. ClickBench on a 50-million-row DataFrame: 219 seconds down to 20, 10.9 times less total time; the geometric mean across queries is 4.5. This one needs no free-threading. It works on the Python you already have. So the ranking on a hot path: avoid Python objects entirely if the layout lets you; if not, read them as cheaply as CPython allows. Zero-copy removes a tier. Free-threading fixes the tier you cannot remove.
Part 4 · What broke
04

Three bugs the GIL had been hiding

Crashes hid as hangs. A segfault turned into a deadlock inside the crash handler. No traceback.
Cold start with 32 threads hung. The garbage collector waited for a thread stuck in our own lock.
Above 8 threads the UDF slowed down. One throwaway object per row kept waking the garbage collector.
Free-threading did not create these bugs. It revoked the amnesty.
Part four. Three bugs, all of them older than the port. Crashes turning into hangs is worse in a service than in a script, because a hung call looks like a slow one. The second one is the import-cache initializer from part three. It resolves Python types, so it can allocate, so it can trigger a garbage collection. The free-threaded GC stops the world and waits for every attached thread to reach a safe point. The other threads were blocked inside std::call_once, still attached, never reaching one. Everything froze. The fix: detach from the interpreter before you block on a C++ primitive, or use PyMutex, which detaches for you. Third, UDF throughput collapsed past eight threads because per-row argument tuples were feeding GC storms. Reusing the argument frame with Vectorcall fixed it and cut the call overhead 4.7 times. The free-threaded GC is more sensitive to allocation churn, not less. We found the last two only by benchmarking.
Part 4 · Decision guide

Where no-GIL helps, and where it does not

No gain when…

Your library already runs its heavy work outside Python (numpy, Polars, pyarrow). 0.161 s on both builds.
You can avoid PyObjects entirely (Arrow, buffers).
Single-threaded work — one Airflow task — pays ~1–8%.

Real gain when…

Many threads must execute Python: UDFs, callbacks.
Many threads must read PyObjects: object columns.
Many concurrent callers in one process — a service running many of those tasks.
Free-threading fixes what zero-copy cannot reach: running Python in parallel.
Anything that already ran outside the GIL did not get faster: the pure-engine query, no Python objects involved, was 0.161 seconds on both builds. Anything we could make zero-copy got faster without free-threading, and got more from that than from the lock going away. And a single-threaded job pays the small tax for nothing. Where it paid: whenever many threads have to run Python or read Python objects. The scoring function in the query. The object column of tool output. And the case that started all this: many callers in one process, each holding Python state, each wanting the engine now. If you keep Python out of the query, stay on stock. If you want Python in the query, this is what makes it scale.

Part 5 · What it buys

Agent queries and pandas jobs, one process

import chdb.datastore as pd     # pandas API, ClickHouse engine
sess = chdb.session.Session("./brain")
@func([STRING, STRING], FLOAT64)
def score(text, q): return reranker(text, q)
def recall(user, q):            # an agent tool call
    sql = ("SELECT text, score(text, {q:String}) AS s "
           "FROM memory WHERE user_id = {user:String} "
           "ORDER BY s DESC LIMIT 8")
    return sess.query(sql, "DataFrame",
                      params={"q": q, "user": user})
def report(day):                # a pandas job
    ev = pd.read_parquet("s3://lake/events/*.parquet")
    return ev[ev.ts >= day].groupby("user_id").amount.sum()
with ThreadPoolExecutor(16) as pool: ...   # both at once

On stock Python

The pandas chain becomes one SQL on every core. Faster than pandas on 14 of 16 everyday ops, ⅓ the RAM.*

3.14t adds

Many of these jobs in flight, one model in memory. No worker pool.

* We measured: 10M-row Parquet vs pandas, one laptop. Sorts ×35–×52; peak RSS 1,059 → 440 MB.

A pool of queries in flight. One interpreter. Zero subprocesses.
This is the pattern. One process, one reranker loaded once, a thread pool. recall is an agent tool call with a Python scoring function inline. report is a pandas chain over Parquet on S3; it compiles to one SQL and runs on the engine, and that part works on stock Python today, at the numbers in the blue card. On stock Python the pool is decoration: every path funnels through the GIL. On 3.14t the pool is real. No worker processes, no pickling, one copy of the model. This is a sketch, not a benchmark. The numbers were the previous slide.

This is the slide to photograph. Three steps. Install: uv will fetch the free-threaded build if you ask for 3.14t; the python.org installer has a free-threaded checkbox. Check: import your whole stack, then print the flag. False means the GIL is off. If you see the RuntimeWarning, one of your packages has not opted in and dragged the GIL back for the whole process; the message names it. You can force the GIL off with PYTHON_GIL=0, but that hides the warning, so check first, force second. The community tracker tells you which packages are ready before you try. Try: install chdb, define a small Python function and call it from SQL with eight engine threads. The parallelism is inside the query: eight engine threads each call your function per row. On stock they take turns at the lock; on 3.14t they do not. Time it on python3.14 and on python3.14t and you will see the difference on your own laptop. This is the same shape as the bike-lane benchmark, deliberately: one query, engine threads, a Python function in the middle.
