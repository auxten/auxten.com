Porting a C++ Python extension to free-threaded Python 3.14

Auxten Wang · Technical Director @ ClickHouse · Creator of chDB

One story. What it took to make a C++ extension faster on free-threaded Python, and what we measured at the end. The workload that hurt us was many concurrent queries from one Python process, most of them coming out of our own agent tool loops. The GIL sat in the middle of every one of them. Every core, one process, no worker pool: that is the target. Numbers at the end.

Part 1
01

The problem

A parallel engine, one lane into Python.

Part one, the problem. What chDB is, exactly where the GIL bit it, why the usual workarounds did not apply, and why the agent era made it urgent.
chDB

chDB: the ClickHouse engine inside your Python process

pip install chdb

sess = chdb.session.Session("./brain")
sess.query("""
  SELECT m.text FROM memory m
  JOIN s3('s3://lake/events/*.parquet') e USING (user_id)
  JOIN Python(tickets) t USING (user_id)
  WHERE m.user_id = 'u1' LIMIT 8""")
For those who do not know ClickHouse: the open-source columnar analytics database. chDB is that whole engine as a pip install, living inside your Python process, no server. Local tables on disk, files on S3, a Postgres table, a live DataFrame: all tables in one statement. That is all the ClickHouse you need for this talk. What matters: the engine is heavily multi-threaded C++, glued to Python by pybind11, and it calls into Python in two places that hurt: user-defined functions and strings.
Bottleneck 1

Bottleneck 1: a Python function, called per row

This is the picture for the whole talk. Left, the engine: many threads, parallel by design. Right, Python. On a stock interpreter that is one lane. The first place we hit it: a user-defined function, your Python function called from SQL once per row. A reranker scoring memory entries against the question, an embedding, a tokenizer. Every engine thread reaches the call and waits its turn. We measured a four-million-row scalar UDF on a 16-core box: about 0.85 seconds, and it did not matter whether the engine used one thread, eight, or thirty-two. Flat. That flat line is the problem.
Bottleneck 2

Bottleneck 2: one Python object per string

More threads, slower. Same for object-dtype DataFrames.

Second place. Agent memory is text all the way down: chat logs, tool output, JSON. In pandas, an object column of text is one Python object per cell, and every one of them has to be read under the lock. A scan over five million such strings: stock Python, few threads, 0.13 seconds. Give the engine 16 threads and it gets slower, 0.22, because they pile onto the lock. Everything I just said about strings applies to any object-dtype DataFrame crossing into or out of the engine. Two bottlenecks, one cause.
Workarounds

How Python has lived with the GIL

Release it inside C loops
Fork a process pool
Compile it away: Cython, Numba
asyncio for the waiting
Batch, so glue amortizes
None of this is new, and the ecosystem has coped well. numpy and friends release the lock around their C loops, so the heavy work runs on all cores and Python only orchestrates. multiprocessing, joblib, DataLoader workers: fork, and pay for it in copies. Cython's nogil blocks and Numba leave the interpreter entirely. asyncio hides waiting, which is I/O, not compute. And batching: hand the C side a big array so the per-call glue does not matter. Five hatches, one shared assumption: Python sits at the edge, handing work to something else.
Workarounds

Every workaround assumes Python is at the edge. Ours is in the middle.

A per-row callback is Python
Object strings are read under the lock
Fork pool: reload the model, pipe text
Now hold those hatches against our two problems. Release the GIL inside the loop? The loop calls back into Python once per row. There is nothing to release; the work is Python. Read strings outside the lock? A Python string is a Python object; touching it is a lock operation. Fork a pool? We did. chDB's original UDF path forked a fresh interpreter per query and piped rows through as text. The model you had loaded was loaded again, inside the fork. That 0.85 seconds flat was with the workaround. The hatches work when Python is the coordinator at the edge. Here the engine is the coordinator and Python is in the middle of the hot loop.
Agents

An agent's tool loop pays the lock on every call

Now the reason this stopped being a niche complaint. A chatbot is one request. An agent is a loop: plan, call a tool, read the result, call another. Most tool calls are data access with Python in the middle: a recall query with a reranker inside it, a Parquet read followed by an embedding, tokenizing logs before filtering them. In a multi-threaded agent process several of these are in flight at once, and every one of them touches Python objects. So every one of them queues at the lock. Embedding, reranking, tokenizing are interleaved with reads and queries in the same process, and that mix is what the GIL serializes worst: never enough pure C work to release the lock for long.
Agents

So the GIL shapes how Python builds agents

A process pool per tool
Memory moved to a remote service
Logic moved out of Python
Look at how agent stacks are built and you see the lock in the architecture. Tools run in worker processes, so state is pickled and models are loaded per worker. Memory goes to a remote service, so every recall pays a network round trip; we measured the same recall query at a p95 of 1.7 milliseconds in-process against 93 milliseconds over a network with half a percent packet loss. Or the logic leaves Python altogether. None of these are wrong; they are what you do when one interpreter runs one thread. A diagnosis, not a complaint: the lock has been an architectural constraint, and the agent era made it visible.

What we did

What finally changed, and what it bought us.

Part two. First, what finally changed in Python itself, because that took 29 years. Then the three steps we took with it, each with its own number, and what the result means for how you build.
What changed

Removing the GIL: 29 years of tries

Thirty seconds of history, because it explains the tax. The yardstick is Guido's, from 2007: he would take GIL removal only if single-threaded programs did not get slower. Every attempt here was measured against that sentence. 1996: Greg Stein removed the GIL from Python 1.4 with fine-grained locks. It worked, and single-threaded code ran nearly twice as slow, so it died. 2009: Antoine Pitrou rewrote the GIL for 3.2: fairer scheduling, same lock. 2016: Larry Hastings' Gilectomy; every refcount became an atomic operation, the interpreter crawled, abandoned. 2017 on: Eric Snow gave each sub-interpreter its own GIL in 3.12. A sidestep, not a removal. 2021: Sam Gross's nogil fork solved the refcount problem with biased reference counting and immortal objects, kept single-thread speed within a few percent, and became PEP 703. Every failure was the same failure: single-thread speed. Next: how the last one got under the bar.
What changed

Why nogil passed: no big trick, four small ones

Biased refcounting

Owner counts without atomics.

Immortal objects

Never refcounted at all.

Deferred refcounting

Stack refs skipped; GC checks.

Per-object locks

One tiny lock per container.

Result: ~1–8% single-thread cost. Guido's rule, met.

Not one big idea: a stack of small ones, each avoiding shared memory. Biased reference counting: every object remembers its creating thread; that thread bumps a plain counter, everyone else uses a second, atomic one. Immortal objects: None, True, small integers and interned strings are never counted at all, so the hottest objects are never contended. Deferred reference counting: functions, modules and code objects are pushed and popped constantly; the interpreter skips those counts and the cycle collector settles up. Per-object locks: a one-byte lock in every list and dict, reads mostly lock-free, writes take that object's lock only. Together: a few percent single-thread cost, under Guido's bar. And that is the tool we picked up.
Step 1 · UDF inside

Free-threading cannot speed up a fork()

A fresh interpreter per query
Rows piped as text
Your model, loaded again per fork
Step one starts with an admission: our Python UDFs did not run in the process at all. The decorator generated a script, the engine forked a fresh interpreter, rows went through as tab-separated text. For a scoring or embedding function that was fatal: the model you had loaded was not there. It got loaded again, per fork, per query. Free-threading would have done nothing for this design; there was no Python in our process to parallelize. So step one has nothing to do with the GIL. It is the prerequisite.
Step 1 · UDF inside

UDF inside the process. On stock: still 0.85 s.

from chdb import func
from chdb.sqltypes import STRING, FLOAT64

@func([STRING, STRING], FLOAT64)
def score(text, q):
    return reranker(text, q)  # loaded once

sess.query("SELECT text, score(text, 'S3 cost') AS s "
           "FROM memory ORDER BY s DESC LIMIT 8")
After: the decorator registers a real Python callable and the engine's worker threads call it with typed arguments, using the model the process already has. No fork, no text protocol. Under the hood each worker thread takes a gil_scoped_acquire before the call. Correct, necessary, and on a stock interpreter that acquire is the lock: the threads still take turns. So on stock Python this step, alone, is still 0.85 seconds, flat. It proves nothing yet. What it does is put Python inside the process, so that the next step has something to unlock.
Step 2 · Flip the switch

One line, one promise: nothing here needs the GIL

// pybind11 ≥ 2.13
PYBIND11_MODULE(_chdb, m,
    py::mod_gil_not_used())
Step two is one line; the raw C API has the same slot, Py_mod_gil. The line is a promise: nothing in this module relies on the GIL for correctness. Keeping it meant auditing every global: the type cache, the UDF registry, the engine singleton. Each needed a real lock. Borrowed references, pointers you do not own, became strong ones wherever another thread could mutate the container underneath us. None of it is clever. The GIL had just been hiding the to-do list.
Step 2 · Flip the switch

Our import cache raced for years. The GIL was its alibi.

First NULL → a lazy import
Segfault, far from the bug
Then a hang. No traceback.
The human beat. Our import cache, the thing that resolves pandas and numpy types, had a lock-free fast path that had been a race for years. The GIL was its alibi. We fixed the race with a one-shot initialiser, and that exposed the bug it had been hiding. First NULL in a string column, and a scan thread lazily imports pandas.NaT from a thread that was not attached to the interpreter. Segfault inside the allocator, nowhere near the cause. Then the crash handler deadlocks: no traceback, no exit, the query just hangs. The fix was two lines, resolve those attributes eagerly at module init. Finding it took days. Free-threading bugs do not crash loudly. They go quiet.
Step 2 · Result

Same UDF, 8 threads: 0.85 s → 0.15 s

And now the number, after the switch. Stock 3.14 is one bike lane: many engine threads, one of them runs Python at a time, so the number does not move with thread count, about 0.85 seconds. 3.14t gives every thread its own lane: one thread 0.72 seconds, eight threads 0.15, flat to 32. Same C++, same acquire; on 3.14t that acquire is per-thread bookkeeping, not a global lock. One reading caveat: 0.85 is the contended number, so do not read 0.85 against 0.72 as the single-thread tax; that is a different measurement. One obligation: your UDF now runs concurrently, so it has to be thread-safe. A dict used as a cache still races on "if key not in cache, compute and store".
Step 3 · Strings

Strings: go straight to the bytes

// FillColumnString, free-threaded build
if (PyUnicode_IS_COMPACT_ASCII(obj)) {         // logs, ids, keys
    data = (const char *) PyUnicode_1BYTE_DATA(obj);  // no copy
    len  = PyUnicode_GET_LENGTH(obj);
} else {
    data = PyUnicode_AsUTF8AndSize(obj, &len);  // thread-safe
}
Step three, the string path. Millions of strings cross the border per query, and each went through a pybind11 shim and a friendly Unicode API, one call per value. The free-threaded build cannot use the stable ABI anyway, so nothing was lost by going low-level: direct CPython calls. Compact ASCII, which most logs, identifiers and JSON keys are, is a pointer and a length, no copy, and that buffer is immutable, so any engine thread may read it. Everything else goes through PyUnicode_AsUTF8AndSize, the public call. We first read CPython's cached UTF-8 field directly; that field is filled lazily and reading it from another thread is a data race on 3.14t. The public call handles that.
Step 3 · Result

Object strings, 16 threads: 0.22 s → 0.08 s

The result for object strings: the same five-million-string scan from the problem slide. Stock at its best, fewer threads, 0.13 seconds. Stock at 16 threads, 0.22, slower. 3.14t at 16 threads, 0.08. Two ratios, and you should hear both: 1.6 times against stock's best run, 2.6 times against stock at the same thread count. On stock, adding threads made it slower; on 3.14t, faster. Setup: 56-vCPU Xeon, CPython 3.14.6 against 3.14.6t, minimum of six runs.
Step 3 · Result

219 s → 20 s. Not the lock: zero-copy.

object dtype
one Python object per row
219.2 s
Arrow-backed
plain buffers, no Python objects
20.1 s

Works on stock Python today.

And then the biggest single win, which was not the lock. pandas 3 with PyArrow stores string columns the way Parquet does: a validity bitmap, an offsets array, one contiguous buffer. Every engine thread reads that directly, zero-copy, and no thread touches a Python object. ClickBench on a 50-million-row DataFrame, 43 queries: 219 seconds down to 20, 10.9 times less total time; geometric mean 4.5, string-heavy queries up to 64 times. This needs no free-threading. It works on the Python you have today. The ranking on a hot path: avoid Python objects if the layout lets you; free-threading is for the ones you cannot avoid.
Scorecard

Scorecard: the lane is gone

The picture from the start, fully open. Same engine threads on the left; on the right, a lane per thread. Three numbers, three different stories. The UDF: 0.85 to 0.15 at eight threads, pure free-threading, once the function lived in the process. Object strings: 0.22 to 0.08 at 16 threads, free-threading plus the lighter string path. Arrow columns: 219 to 20 seconds, and that one is zero-copy, not the lock; it works on the Python you have today. For the record: our pure-engine query, no Python objects, ran 0.161 seconds on both builds. Same engine, same speed; only the Python touchpoints moved.
Looking back

Agent tool calls and pandas jobs, one process

Looking back, this is what the port bought. One process. Agent tool calls come in on the left, a recall query with a Python reranker inside it. pandas jobs come in next to them, a Parquet aggregation over S3. The engine serves them on its own threads, and the Python parts run in parallel too. One copy of the model, loaded once. No worker pool, no pickling, no remote memory service on the hot path. Sketch, for the notes reader: a @func score(text, q); recall(user, q) runs one SQL with score inside; report(day) is a chdb.datastore chain over Parquet; both go to one ThreadPoolExecutor. A sketch, not a benchmark.
Looking back

pandas chain → one SQL + in-process UDFs

Measured, stock Python

14 of 16 ops faster

sorts 35–52× · RAM 1,059 → 440 MB

Design argument, 3.14t

Many chains in flight, one process.

pandas op → SQL + UDF, naturally.

The pandas side of the same story. chdb.datastore is a pandas-compatible layer: you write the chain, it compiles to one SQL and runs on the engine, and anything that has to stay Python becomes an in-process UDF. Left card is measured: a 10-million-row Parquet against pandas on one laptop, faster on 14 of 16 everyday operations, sorts 35 to 52 times faster, peak memory 1,059 down to 440 megabytes. That is on stock Python; we showed it at PyCon JP. Right card is the design argument, not a benchmark: with the GIL off, many of those chains run concurrently in one process, and pandas operation to SQL plus Python UDF stops being a compromise, because the UDF now scales too.
Ecosystem

60% of top compiled packages ship 3.14t wheels. One holdout re-locks the process.

$ python3.14t -c "import yourstack"
RuntimeWarning: The global interpreter lock (GIL) has been enabled
  to load module 'X', which has not declared that it can run safely
  without the GIL.
Where the ecosystem is today: 216 of the 360 most-downloaded compiled packages ship free-threaded wheels, 60 percent as of this week. numpy, pandas, PyArrow, SciPy, scikit-learn, PyTorch are in. Still missing: grpcio and protobuf, which block much of the AI tooling tree, DuckDB, tokenizers, orjson. Why the holdouts matter more than the percentage: import one extension that has not declared itself safe and CPython turns the GIL back on for the whole process, with this warning. Your other forty packages did the work and get nothing. So this is a per-process property decided by your weakest dependency, and the warning names it.
