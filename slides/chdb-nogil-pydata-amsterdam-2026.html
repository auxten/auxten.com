Porting a C++ Python extension to free-threaded Python 3.14

Auxten Wang · Technical Director @ ClickHouse · Creator of chDB

Thirty minutes, one story: what it actually took to make a C++ extension benefit from free-threaded Python, and what we measured at the end. This is not a history talk. If you want the PEP 703 saga, find me after. The honest reason we did this port: the workloads that hurt in 2026 were many concurrent queries from one Python process, most of them coming out of AI-agent tool loops, and the GIL sat in the middle of every one of them. Sixteen cores, one process, no worker pool: that is the target shape, and I will show the numbers when we get to the benchmarks.

Part 1 · Why it matters
01

Why free-threaded Python matters for native extensions

3.14 runs Python on every core. Your C extension does not get that for free.

Part one, about four minutes. One slide on why we bothered, one on what changed in 3.14, one on why extensions do not benefit automatically.
Part 1 · The motivation

Why we bothered: many queries, one process

The load started looking like an agent's tool loop: one interpreter, many threads.

Recall

Filter + rank a memory table.

Federate

S3 + Postgres + a DataFrame. One SQL.

Score in Python

A Python function, per row.

Hand back a frame

Results back as DataFrames.

Sixteen engine cores were ready. The Python side was single-file.

The engine was multi-threaded. The process it lived in was not.
This is the honest "why". A chatbot is one request. An agent is a loop: plan, call a tool, read, call another tool, typically five to twenty times per turn, and most of those calls are data access. Recall over a memory table, a federated query joining a lake file with a live database and whatever the last tool returned, a Python function inside that query to score rows, and the result handed back as a DataFrame. We had already won the latency argument for putting the data layer in-process: our local-vs-remote benchmark measured in-process recall at p50 1.1 ms against 63 ms for the same query over the wire, with a p99 tail that reaches seconds when the network hiccups (github.com/auxten/agent-local-vs-remote). But once everything runs inside one process, that process has to use the machine. Sixteen engine threads were ready. The Python side was single-file. That is the itch. Data engineers in the room: the same shape shows up as a service that runs many pandas-style jobs from one process. Same lock.
Part 1 · Python 3.14t

What 3.14 changes — all the history you get today

PEP 703 → PEP 779

GIL optional in 3.13. Supported in 3.14.

A separate build

python3.14t, cp314t wheels. ~5–10% single-thread cost.

The stack moved

61% of top compiled packages ship 3.14t wheels.

$ python3.14t -c "import sys; print(sys._is_gil_enabled())"
False        # threads now run Python bytecode in parallel
One slide of context. The rest is engineering.
Deliberately one slide. PEP 703 made the GIL optional in 3.13 as an experiment; PEP 779 made it supported in 3.14. It is a separate interpreter binary, python3.14t, and a separate wheel tag, cp314t. The single-thread penalty came down from roughly 40 percent in 3.13t to 5 to 10, which is what made it usable. The ecosystem followed: as of July, 61 percent of the top 360 compiled packages ship free-threaded wheels, per hugovk's tracker, and manylinux dropped 3.13t, so 3.14t is the only free-threaded target worth building for. The engineering under it, biased refcounting, immortal objects, per-object locks, lock-free dict and list reads, is why it is fast, and also why a borrowed reference that was harmless for thirty years is now a use-after-free. That is the whole history lesson.
Part 1 · The catch

Your extension gets nothing for free

One undeclared import turns the GIL back on for everyone.
"Thread-safe because GIL" is now a data race.
No stable ABI on 3.14t. New wheels, new CI.
$ python3.14t -c "import _chdb"
RuntimeWarning: The global interpreter lock (GIL) has been enabled to load
module '_chdb', which has not declared that it can run safely without the GIL.
Free-threading is opt-in, per extension module. This talk: what opting in took.
Three things bite extension authors. First, the silent re-enable: import one extension that has not declared itself safe and CPython turns the GIL back on for everyone, with a warning most people never read. Second, twenty years of code that was thread-safe only because the GIL serialized it. Third, the stable ABI does not exist on the free-threaded build, so your abi3 wheel is out; you build and ship cp314t wheels separately. The practical consequence for us: a process running sixteen concurrent queries on 3.14t got zero benefit, because our module was the undeclared import. That warning is us. Fixing it is the rest of the talk.

Part 2 · The toll gate

Parallel engine × serial glue = serial query

Python UDF calls

score(text, q) per row. Sixteen streams, one lock.

String-heavy columns

Chat logs, tool output, JSON: one PyObject per cell, read under the lock.

DataFrame integration

pandas in, pandas out. chdb.datastore turns a pandas chain into one SQL — the frame still crosses the lock.

The GIL did not slow the engine down. It serialized every conversation with Python.
The picture: sixteen engine threads on the left, happily parallel, all queuing single-file at the GIL to reach three things on the right. Python UDFs: a function that scores or embeds rows calls back into the interpreter per row, and on a stock build sixteen streams take turns. Strings: agent memory is text all the way down, chat logs, tool output, JSON, and a pandas object column of that is one PyObject per cell, each read under the lock. And the DataFrame path, which matters most to this room: data engineers live in pandas. chdb.datastore is our pandas-compatible API; it records a pandas chain and compiles it into one SQL statement for the engine. Every frame that goes in or comes out still has to cross this border, with NULL checks and dtype lookups that are each a tiny Python call. The engine was never the bottleneck. The border was.
Part 3 · Three changes
03

Three changes that unlocked parallelism

Restructure, then remove the lock, then go low-level where the rows are.

01

Run Python UDFs in-process

02

Declare the module GIL-independent

03

Rework the string hot paths

The meat, about twelve minutes. Three changes in the order we made them, and the order matters: first restructure so that there is something for free-threading to speed up, then the one-line declaration and the audit behind it, then the string hot paths, which is where most of the bytes actually are.
Change 1 · UDFs

UDFs ran out of process

fork() a Python interpreter per query
Rows piped as text. Every argument a str.
Your loaded model? Loaded again, per fork.

The bottleneck was fork(), not the GIL.

Change one, and it starts with an embarrassing admission. Our Python UDFs did not run in the process at all. The decorator generated a script and an XML config, the engine forked a fresh interpreter, and rows went through as tab-separated text. Every argument arrived as a string. For a scoring or embedding UDF this was fatal: the model you had already loaded in the process was not there. It got loaded again, inside the fork, per query. Free-threading would have done nothing for this design. There was no Python in our process to parallelize. So step one had nothing to do with the GIL.
Change 1 · UDFs

After: native in-process UDFs

from chdb.sqltypes import STRING, FLOAT64

@func([STRING, STRING], FLOAT64)
def score(text, q):
    return reranker(text, q)  # loaded once

sess.query("""
  SELECT text, score(text, 'S3 cost') AS s
  FROM memory ORDER BY s DESC LIMIT 8""")
// C++: engine worker threads call it
py::gil_scoped_acquire acquire;  // THE lock

for (size_t row = 0; row < rows; ++row)
{
    py::tuple  args = box_arguments(row);
    py::object out  = func(*args);
    insert_into_column(result, out);
}

Faster already. But on a stock build, every engine thread queues on that acquire.

After: the decorator registers a real Python callable, C++ keeps a py::function, and the engine's worker threads call it with typed arguments. The example is a reranker scoring rows against the current question, using the model the process already has. No fork, no text protocol. Now look at the C++ on the right. One line, gil_scoped_acquire. Correct, necessary, and on a stock interpreter it is the toll gate: sixteen engine threads reach that line and take turns. We had moved the Python into the process precisely so that free-threading would have something to work on. Next slide is what happened when it did.
Change 1 · UDFs

This is what no-GIL was made for

Stock: 0.85 s flat, any thread count
3.14t: 0.72 → 0.15 s from 1 → 8 threads. Holds at 32.
Your UDF runs concurrently now. Make it thread-safe.

4M-row scalar UDF, 16-core x86_64. Vectorcall later cut boxing 4.7× (chdb-core #142).

Order matters: in-process first, then remove the GIL.
Amsterdam picture. Stock 3.14 is one bike lane: sixteen engine threads, one of them runs Python at a time, the rest queue. On the 4M-row scalar UDF that was a flat 0.85 seconds no matter how many threads we gave it. 3.14t gives every thread its own lane. Same C++, same gil_scoped_acquire, but on the free-threaded build that acquire is per-thread bookkeeping, not a global lock. 0.72 seconds on one thread down to 0.15 on eight, and it held at 32. Two caveats, both honest. Your UDF now runs concurrently, so it has to be thread-safe; a model forward pass usually is, a plain dict you use as a cache is not. And boxing arguments per row still costs; switching to PyObject_Vectorcall with a reused argument frame took another 4.7x off that overhead, chdb-core PR 142. This benchmark UDF is trivial on purpose: it measures the calling floor under any real scoring function. TODO if time allows before Thursday: the same curve with an actual reranker model. A subprocess pipeline gains nothing from free-threading, which is why the order was in-process first.
Change 2 · Opt in

Opting in: one line, and an audit

// pybind11
PYBIND11_MODULE(_chdb, m,
                py::mod_gil_not_used())
// raw C API
{Py_mod_gil, Py_MOD_GIL_NOT_USED},

The line is easy. It is a claim about every global in your codebase.

Caches, registries, singletons → call_once, shared_mutex, PyMutex
Borrowed → strong refs: PyList_GetItem → PyList_GetItemRef
Our import cache had raced for years. The GIL was its alibi.
None of the fixes were exotic. The GIL was just hiding the to-do list.
Change two is one line in two dialects: py::mod_gil_not_used() in pybind11, or the Py_mod_gil slot with Py_MOD_GIL_NOT_USED in the raw C API. We compile it in only for the free-threaded build, because that build also forced us off the stable-ABI pybind11 fork and onto upstream pybind11, which is its own CI matrix. The line itself is a promise: nothing in this module relies on the GIL for correctness. Keeping that promise meant auditing every global. The import cache that resolves pandas and numpy types, the UDF registry, the engine singleton, the dtype caches. Each got a real primitive: call_once for one-shot init, shared_mutex where readers dominate, PyMutex where Python objects are involved. And borrowed references became strong ones wherever another thread could mutate the container underneath us. None of it is clever. The uncomfortable finding was that our import cache's supposedly lock-free fast path had been a race for years. The GIL had been covering for it.
Change 2 · Shared state

Fix the race, then the bug it was hiding

// ImportCache() — on the per-row scan path
#ifdef CHDB_FREE_THREADING
  // no global mutex: this runs per row
  static std::once_flag init_flag;
  std::call_once(init_flag, [] {
      cache = std::make_shared<ImportCache>();
  });                     // lock-free after
#else
  if (!cache)             // GIL serializes
      cache = std::make_shared<ImportCache>();
#endif

Trigger. First NULL in a string column → lazy import of pandas.NaT, no thread state.

Crash. Segfault in the allocator, far from the bug.

Hang. Signal handler deadlocks. No traceback. Forever.

Fix: resolve imports eagerly, while you hold the GIL.

Debugging silence is the expensive part. Budget for it.
Left is the actual code from the import cache, because it shows the trade-off. This function sits on the per-row scan path. A global mutex would have been correct and would have serialized every scan thread once per row, which defeats the point. call_once gives a one-shot init and a lock-free read afterwards; the initializer is pure C++, no Python calls, so it cannot recurse into the interpreter or block on a lock it is holding. Right is the bug that fixing the race exposed. First NULL in a string column, which in real data is every other row. A scan thread lazily imports pandas.NaT, from a thread that has no Python thread state. Segfault inside the allocator, nowhere near the cause. Then the fatal-signal handler deadlocks, so no traceback, no exit, the query just hangs. In a long-running service that looks like a request that never returns. The fix was two lines: resolve those attributes eagerly at import time, while you hold the GIL. Finding it was days. Free-threading bugs do not crash loudly; they go quiet.
Change 3 · Strings

Strings are the hot path: go straight to the bytes

// FillColumnString — free-threaded build
if (PyUnicode_IS_COMPACT_ASCII(obj)) {                 // most logs, ids, keys
    data = (const char *) PyUnicode_1BYTE_DATA(obj);   // pointer, no copy
    len  = PyUnicode_GET_LENGTH(obj);
}
else if (auto * u = (PyCompactUnicodeObject *) obj; u->utf8) {
    data = u->utf8;  len = u->utf8_length;             // no copy
}
// ...other kinds transcoded
ASCII str → a pointer read. Immutable, so thread-safe.
No stable ABI on 3.14t anyway. Go low-level.
On hot paths, the friendlier the API, the more it costs per row.
Change three, strings. For a memory table or a log, strings are not metadata, they are the payload. Millions of them cross the C++/Python border per query, and every one went through a pybind11 shim and a friendly Unicode API, one call per value, each touching the interpreter. The free-threaded build cannot use the stable ABI at all, which turned out to be liberating: we replaced the limited-API wrappers with direct CPython calls. If the string is compact ASCII, which most logs, identifiers and JSON keys are, it is a pointer and a length; no copy. If CPython already cached a UTF-8 representation, we use that; still no copy. Only the 2- and 4-byte kinds get transcoded. A str is immutable, so reading its buffer from any engine thread is safe without a lock. This is the actual code from FillColumnString under the free-threading define, slightly compressed.
Change 3 · Strings

The biggest win: skip PyObject entirely

pandas 3.x str columns are Arrow-backed: plain C buffers, no GIL at all.

object dtype — 219.2 s
Arrow zero-copy — 20.1 s

ClickBench, 50M-row DataFrame · 10.9× total · string queries up to 64×

chdb.datastore hands back Arrow-backed frames — the same win, in a pandas-shaped API.

Priority: no PyObject > cheap PyObject access > friendly PyObject APIs.
And then the biggest single win had nothing to do with locks. pandas 3 makes string columns Arrow-backed by default: a validity bitmap, an offsets array and one contiguous data buffer. Plain C memory. Every engine stream reads them directly, zero-copy, and no thread ever touches a PyObject. ClickBench on a 50-million-row hits DataFrame, all queries, pandas 3.x, hot run: 219 seconds to 20; geomean 4.5x; string-heavy queries up to 64x. For the pandas people: this is exactly the path chdb.datastore uses. You write a pandas chain, it compiles to one SQL, the engine runs it on every core and streams, and the frame you get back is Arrow-backed. In the PyCon JP measurements on a 10M-row Parquet, that API was faster than pandas on 14 of 16 everyday ops, sorts 35 to 52 times, at a median peak RAM of 440 MB against pandas' 1,059. So the ranking on a hot path: avoid Python objects entirely if the layout lets you; if not, read them as cheaply as CPython allows; friendly APIs only where the row count is small. Free-threading fixes the middle tier. Zero-copy removes the tier.

Part 4 · Scar tissue

What broke, what surprised us

One undeclared dependency: our "no-GIL" benchmark measured the GIL.
Crashes hide as hangs. Segfault → signal-handler deadlock.
No stable ABI: upstream pybind11, doubled CI.
Cold start + 32 threads hung: GC stop-the-world vs call_once.
Per-row arg tuples fed GC storms past 8 threads.

Fixed in chdb-core 26.5.1 (#128, #131).

Free-threading did not create these bugs. It revoked the amnesty.
Five scars. The silent re-enable got us: a real environment has dozens of compiled dependencies, one had not opted in, and our first "free-threaded" benchmark was quietly measuring the GIL. Crashes turning into hangs is worse in a service than in a script, because a hung call looks like a slow one. The stable ABI going away was the biggest structural cost: upstream pybind11 for the free-threaded build, direct CPython calls, doubled CI. Then two we found only by benchmarking. A cold process with a high thread count hung on the first UDF: the free-threaded GC stops the world, and one of our threads was blocked inside a call_once while still attached, so the stop never completed; the fix is to detach from the interpreter before blocking on anything. And UDF throughput collapsed past eight threads because per-row argument tuples were feeding GC storms; reusing the argument frame fixed it. Free-threaded GC is more sensitive to allocation churn, not less. Both fixed in 26.5.1. That is what benchmarks are for.
Part 4 · Decision guide

Where no-GIL did not help, and where it did

No gain when…

Your C++ already releases the GIL. Parity: 0.161 s both.
You can avoid PyObjects entirely (Arrow, buffers).
The workload is single-threaded. You pay ~5–10%.

Real gain when…

Many threads must execute Python: UDFs, callbacks.
Many threads must read PyObjects: object columns.
Many concurrent callers in one process, and you measured it.
Zero-copy beat lock-removal. Free-threading fixes what zero-copy cannot reach: running Python in parallel.
Be fair about it. Anything that already ran outside the GIL did not get faster: the pure-engine query, no Python objects involved, was 0.161 seconds on both builds. Anything we could make zero-copy got faster without free-threading, and got more from that than from the lock going away. And a single-threaded workload pays the 5 to 10 percent tax for nothing. Where it paid: whenever many threads have to run Python or read Python objects. The scoring UDF in the query. The object column of tool output. And the case that started all this: many callers in one process, each holding Python state, each wanting the engine now. That was our measured bottleneck, not a hunch.

Part 5 · What it buys

What this buys: one process, no worker pool

import chdb.datastore as pd            # pandas API
sess = chdb.session.Session("./brain")

@func([STRING, STRING], FLOAT64)
def score(text, q): return reranker(text, q)

def recall(user, q):                    # tool call
    return sess.query(f"SELECT text, score(text, '{q}') AS s "
                      f"FROM memory WHERE user_id = '{user}' "
                      f"ORDER BY s DESC LIMIT 8", "DataFrame")

def report(day):                        # analytics job
    ev = pd.read_parquet("s3://lake/events/*.parquet")
    return ev[ev.ts >= day].groupby("user_id").amount.sum().nlargest(10)

with ThreadPoolExecutor(16) as pool:    # both at once
    ...
One model in memory. No worker pool.
pandas chain → one SQL → every core.
Engine and Python threads share the cores.
Sixteen queries in flight, one interpreter, zero subprocesses.
This is the shape we were after, and it only works on 3.14t. One process holds local tables and one reranker loaded once, and serves two kinds of work from a thread pool. recall is an agent's tool call: a SQL query over the memory table with the Python scoring function inline, returned as a DataFrame. report is what most of this room writes every day: a pandas chain over Parquet on S3. Because it is chdb.datastore, that chain compiles to a single SQL statement and runs on the engine, every core, streaming, and hands back an Arrow-backed frame. In the PyCon JP measurements that API beat pandas on 14 of 16 everyday ops on 10M rows, sorts by 35 to 52 times, at 440 MB median peak RAM against 1,059 for pandas; those numbers are single-process, single-job. What free-threading adds is the pool: sixteen of these in flight at once. On stock Python the pool would be theatre; the UDF, the object columns and the DataFrame conversion all funnel through one lock. On 3.14t engine threads and Python threads share the cores. No worker processes, so one copy of the model and no pickling results across a pipe. If the process itself is disposable, a Lambda or a sandbox, the local tables can also be flushed to object storage and reopened elsewhere, but that is a separate topic. To be clear, this slide is a sketch of the pattern, not a benchmark; the measured numbers are the previous slide.
Part 5 · Checklist

Porting checklist for extension authors

Measure first. Count threads waiting on the GIL.
Restructure first. In-process, then zero-copy, then lock-free.
Declare it: Py_mod_gil / mod_gil_not_used(). No abi3.
Audit every global → PyMutex, call_once, shared_mutex.
Borrowed → strong refs (Py*_GetItemRef).
Resolve imports eagerly, while you hold the GIL.
Detach before you block, or GC deadlocks you.
Cut per-row PyObject churn: Vectorcall, reused frames.
Assert sys._is_gil_enabled() is False in tests.
CI: cp314t lanes + a cold-process, high-thread stress test.

before   port   verify  ·  the long version: py-free-threading.github.io

The list I wish I had. Yellow, before you touch code: measure whether the GIL is actually the bottleneck, count threads waiting on it under real load; and restructure first, because in-process and zero-copy each gave us more than the lock did. Blue, the port itself: declare it, in pybind11 or the raw slot or Cython's freethreading_compatible; audit every global; turn borrowed references into strong ones where another thread can mutate the container; resolve imports eagerly; detach from the interpreter before blocking on anything; and stop allocating per row, Vectorcall with a reused argument frame. Green, verification: assert sys._is_gil_enabled() is False in your tests and treat the RuntimeWarning as a failure, because one dependency silently reverts everything; run the full suite under PYTHON_GIL=0; and give CI a cold-process, high-thread case, because that is where our two nastiest bugs lived. The long version of all of this is the py-free-threading guide; this is the part we personally bled on.
