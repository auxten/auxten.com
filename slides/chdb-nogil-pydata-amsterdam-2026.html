Two places where the engine touches Python

Zero-copy pandas / Arrow

SELECT … FROM Python(df) queries a live DataFrame where it sits. No export, no copy.

Python UDFs

Your Python function, callable from SQL, row by row. Keep this one in mind too.

Two touchpoints, and the rest of the talk is about them. First, the engine reads Python data in place: point a query at a live DataFrame or Arrow table with Python of df, no export. Second, Python UDFs: decorate a function and SQL calls it, per row. No ClickHouse knowledge needed today. For this talk chDB is just a multi-threaded C++ engine behind pybind11, reading Python objects and calling Python functions.
Bottleneck 1

Eight engine threads. One gate into Python. Seven wait.

Two territories. On the left, the engine: eight C++ worker threads that Python does not know about, each on its own block of rows. On the right, the interpreter, and your function lives there. To call it, a thread has to attach and take the GIL. One at a time. While T4 is inside running score, the other seven engine threads stand at the wall, frozen. The timeline: the scan is parallel, then the UDF phase collapses eight lanes into one red line. Four million rows, one, eight or thirty-two threads: about 0.85 seconds. Flat.
Bottleneck 2

A string column is one Python object per cell. Reading a cell takes the lock.

Same wall, other direction. The data lives inside the interpreter this time: an object-dtype column is one Python object per cell, and reading a Python object means holding the GIL. So the engine threads cross the gate for every cell they read, one at a time, and the parallel scan turns serial at the border again. Five million strings, sixteen engine threads, stock 3.14: 0.22 seconds, and adding threads made it slower. This applies to any object-dtype DataFrame crossing into or out of the engine.

Workarounds

Most work has a workaround. Two shapes don't.

Applying a Python function per row

e.g. a user-defined function in a database

Release? The callback is Python.
Compile away? It is the user's function.
Batch? SQL calls it row by row.
Process pool? Copy every block out, load the model per worker.

Processing a PyObject string column

e.g. an object-dtype pandas column read from C++

Release? One PyObject per cell; every read takes the lock.
Vectorize? The cells are not a buffer, they are objects.
Another process? Pickling five million strings costs more than the scan.
The table is right for most code. Those workarounds cover most Python programs, and usually one of them fits. Two shapes have none, and they share one property: Python code has to run per element, in the middle of a multi-threaded C++ loop. A function per row: release the lock? The work is Python. Compile it? It is the user's function. Batch? SQL calls it per row. A pool? Copy every block, a model per worker. A string column: objects, not a buffer. Reading one takes the lock, and pickling five million costs more than the scan.
Agents

One agent turn: six Python steps, one lock

This is any Python agent, one loop iteration. The turn fans out into six steps: an API call, session history, context from files, a tool function, an embedding or rerank, a write back to memory. asyncio handles the waiting. Threads were supposed to handle the rest. The I/O steps do release the GIL while blocked. The CPU steps do not, and every step still takes the lock to touch the dicts, lists and strings it passes to the next one. So "the rest" runs sequentially: a concurrent tool loop executes one step at a time. Our chDB tool call was just one of these steps.
Agents

So the GIL shapes how Python builds agents

A process pool per tool — pickle every dict across
Memory in a remote service — a network hop per step
Logic out of Python — Rust or Go sidecars
Look at how agent stacks are built and you see the lock in the architecture. Three ways around it. Tools run in a process pool: every dict pickled across, a model per worker. Memory and retrieval move to a remote service: a network hop per step. One data point: the same recall query, p95 of 1.7 milliseconds in-process versus 93 over a network with half a percent packet loss, on our test rig. Or the logic leaves Python for a Rust or Go sidecar. None of these are wrong. They are what you do when one interpreter runs one thread. A diagnosis, not a complaint.

What changed

Removing the GIL: 29 years of attempts

Thirty seconds of history, because it explains the cost. The rule is Guido's, from 2007: GIL removal only if single-threaded programs did not get slower. 1996: Greg Stein removed the GIL from Python 1.4 with fine-grained locks. It worked, and single-threaded code ran nearly twice as slow, so it was dropped. 2009: Antoine Pitrou rewrote the GIL for 3.2: fairer scheduling, same lock. 2016: Larry Hastings' Gilectomy. Every refcount became atomic, and the interpreter became much slower. 2017 on: Eric Snow gave each sub-interpreter its own GIL, a way around it, not a removal. 2021: Sam Gross's nogil branch solved the refcount problem, kept single-thread speed within a few percent, and became PEP 703. Every failure was the same failure: single-thread speed.
What changed

Why nogil passed: no big idea, four small ones

Biased refcounting

Owner counts without atomics.

Immortal objects

Never refcounted at all.

Deferred refcounting

Stack refs skipped; GC checks.

Per-object locks

One tiny lock per container.

Result: ~1–8% single-thread cost. Guido's rule, met.

Not one big idea: a stack of small ones, each avoiding shared memory. Biased reference counting: every object remembers its creating thread. That thread bumps a plain counter, everyone else uses a second, atomic one. Immortal objects: None, True, small integers and interned strings are never counted at all, so the hottest objects are never contended. Deferred reference counting: functions, modules and code objects are pushed and popped constantly. The interpreter skips those counts and the cycle collector corrects them later. Per-object locks: a one-byte lock in every list and dict, reads mostly lock-free, writes take that object's lock only. Together: a few percent single-thread cost, within Guido's rule.
Step 1 · Flip the switch

One line, one promise: nothing here needs the GIL

PYBIND11_MODULE(_chdb, m, py::mod_gil_not_used())   // pybind11 ≥ 2.13
Step one is one line. The raw C API has the same slot. It is a promise: nothing in this module relies on the GIL for correctness. This map is what the promise covers. Three kinds of state the GIL used to protect without any code from us. Shared state, anything global: real locks. Object access, the pointers we borrow into Python containers: own what you read. And the engine's own worker threads, which call your Python function: each attaches to the interpreter first. The next three slides take these one at a time.
Step 1 · Object access

Touching an object used to be safe. Not anymore.

PyList_GetItem · borrowed → PyList_GetItemRef · strong Whole C-API families changed with it.
Why the audit exists, in one picture. Thread A asks a list for item zero and gets a borrowed pointer: no refcount taken, because the caller was assumed to hold the GIL. Thread B clears the list. The object's count hits zero and it is freed. Thread A now uses freed memory. With the GIL this could not happen: B could not run while A held the lock. Without it, this happens all the time. The fix is the strong variant, GetItemRef, a reference you own. That rule, own what you read, is what we applied everywhere we borrow from Python.
Step 1 · Shared state

Shared state: every "safe because GIL" spot got a real lock

Shared state next. Three globals in chDB had been thread-safe by accident: the cache of imported Python types, the registry of user functions, and the engine singleton. Each was written once and read by many threads, and the GIL made that fine. Each now has an ordinary C++ primitive: a one-shot initialiser, a reader-writer lock, a plain mutex around engine start-up. Nothing exotic. The work was not the locks. It was reading the code as if the GIL did not exist, and finding every place where it had been protecting us without anyone asking.
Step 1 · Engine threads

3.14t: a gate per thread. Eight in Python at once.

Same code. py::gil_scoped_acquire on every worker thread: on stock Python one shared lock, on 3.14t per-thread bookkeeping.

Same picture, free-threaded. The engine's worker threads are still C++ threads that Python does not know about. Before one may call your function it attaches: gets its own interpreter thread state, the yellow tag. On stock Python that same acquire line is the one global lock and eight threads queue at one gate. On 3.14t it only registers the thread, so the wall has a gate per thread and eight calls run at once. The code in the UDF path did not change. The timeline: eight red segments overlap instead of lining up.
Step 1 · Result

Same UDF, 8 threads: 0.85 s → 0.15 s

And the number. Stock 3.14 is one bike lane. Many engine threads, but one runs Python at a time. So the time does not move with thread count: about 0.85 seconds at eight threads, the same at 32. 3.14t gives every thread its own lane. The same function goes from 0.72 seconds at one thread to 0.15 at eight, and it holds to 32. Like for like, eight against eight: 0.85 to 0.15. One obligation: your function now runs concurrently, so it has to be thread-safe. A dict used as a cache still races on "if key not in cache, compute and store".
Step 2 · Strings

Strings: stop asking Python for a copy

if (PyUnicode_IS_COMPACT_ASCII(obj)) {               // logs, ids, keys
    data = PyUnicode_1BYTE_DATA(obj);                // pointer, no copy
    len  = PyUnicode_GET_LENGTH(obj);
} else data = PyUnicode_AsUTF8AndSize(obj, &len);  // everything else
Step two, the string path. Millions of strings cross the border per query. Before, each one went through a pybind11 wrapper and a high-level Unicode API. That is one call and one copy per value. On 3.14t that API also writes a cache field inside the object, which needs synchronisation. After: most analytical strings are compact ASCII. Logs, identifiers, JSON keys. CPython stores those as one immutable byte buffer inside the object. We read that buffer where it sits: a pointer and a length. No per-value call, no copy. The thread is still attached and still holds the object. We removed the call and the copy, not the attach. Anything not plain ASCII takes the public call.

Step 2 · Arrow

Or skip Python objects entirely

Background: since pandas 3.0 the default string dtype is Arrow-backed when PyArrow is installed (PDEP-14). Other dtypes are still NumPy; the move to Arrow is not finished.

The bigger change: do not touch Python objects at all. Left, an object-dtype column: every cell is a separate Python object, and reading one means a refcount and, without free-threading, the lock. Right, the same column Arrow-backed, the way pandas 3 with PyArrow stores strings: a validity bitmap, an offsets array, one contiguous data buffer. Plain memory, the Parquet layout. Every engine thread reads those buffers directly: no copy, no Python object, no lock. This needs no free-threading at all. If you are on pandas 3 with PyArrow installed, your string columns already have this layout. The ranking on a hot path: avoid Python objects if the layout lets you. Free-threading is for the ones you cannot avoid.

Looking back

One agent turn on 3.14t: six steps, no lock

This is the agent slide from part one again, with the lock gone. The turn still fans out into six Python steps. The I/O steps behave as before. The CPU steps now run in parallel, and the dicts, lists and strings passed between steps no longer need a shared lock. Our chDB tool call, or a pandas job, is just one of the six. One copy of the model, loaded once. The process pool, the remote memory service and the sidecar from part one are no longer forced on you. A sketch of the shape, not a benchmark.
Looking back

A pandas chain becomes one SQL query

import chdb.datastore as pd
df = pd.read_parquet("events.parquet")
top = (df[df.status == 200]
         .groupby("user_id").amount.sum()
         .sort_values(ascending=False)
         .head(10))
SELECT user_id, sum(amount) AS amount
FROM file('events.parquet')
WHERE status = 200
GROUP BY user_id
ORDER BY amount DESC
LIMIT 10

One compiler

Ten chained ops → one plan. No intermediate copies.

Every core

pandas computes on one core. The engine fills them all.

Streaming

Top-10 of 10M rows keeps a 10-row heap, never the sorted table.

The pandas side of the same story. chdb.datastore is a pandas-compatible layer that ships with chDB: change the import, keep the code. Every call is recorded into a lazy chain. When you ask for a result, a compiler rewrites the whole chain into one SQL statement for the engine, and anything it cannot translate falls back to real pandas mid-pipeline. Three reasons that is faster. One plan instead of one materialized copy per step. Every core instead of one. And streaming: a top-10 over ten million rows keeps a ten-row heap instead of sorting the table, which is why sorts show the biggest gain on the next slide.

Design argument, not measured

With the GIL off, .map(python_fn) inside that chain runs as an in-process UDF on every engine thread.

Measured on one laptop for PyCon JP: a 10-million-row Parquet, read to answer, best of two, outputs identical on all 16 ops. Log scale. Sorts show the biggest gain, 35 to 52 times, because of that heap. Filters and chains, 3 to 22 times. The two red rows are one family: bulk value replace, mask and where. pandas rewrites the column in place. We round-trip it through the engine. Keep pandas there. The break-even point: pandas faster below a million rows, 28 times at ten million, 52.7 on the 100-million-row ClickBench total. The orange card is a design argument, not a measurement.

PEP 779: supported, not default

3.14t is an official build with the same release cadence. You install it on purpose.

The warning, and the override

The warning names the package. PYTHON_GIL=0 forces the GIL off and silences it: check first, force second.

Why your report matters

Free-threading is a per-process property decided by the weakest dependency. One issue on that package unblocks everyone above it.

Why the missing packages matter more than the percentage. Import one extension that has not declared itself safe and CPython turns the GIL back on for the whole process, with this warning. Your other forty packages did the work and get nothing. PEP 779 made 3.14t supported rather than experimental: an official build on the normal release cadence, but not the default. You install it on purpose. The warning names the package that re-locked you. PYTHON_GIL=0 forces the GIL off anyway: useful for testing, dangerous in production because it silences the warning. Check first, force second. And this is why one issue filed against that one package matters: free-threading is a per-process property decided by your weakest dependency.
