Part 1 · Why it matters
01

Why free-threaded Python matters for native extensions

3.14 can run Python bytecode on every core. Your C extension does not get that for free — and the workloads that need it are already here.

4 min
Four minutes on why. I will do one slide on what changed in 3.14 and one on why extensions do not benefit automatically. But first the actual motivation, because it explains every decision that follows.
Part 1 · The motivation

Why we bothered: the process got crowded

In 2026 the load on an embedded engine stopped looking like a notebook and started looking like an agent's tool loop: one Python process, many concurrent tool calls, each one a query.

Recall

"What do I remember about this user?" — filter + vector rank over a memory table. Called before nearly every step.

Federate

One SQL that fans out to Parquet on S3, a Postgres table and a DataFrame in RAM. No pipeline, written at ask-time.

Score in Python

A Python UDF inside that query: embed, tokenize, rerank. The row loop calls back into your code.

Hand back a frame

Results go to the tool loop as a DataFrame. Strings, JSON, timestamps — Python objects, millions of them.

5–20
tool calls per turn
1.1 ms
p50 in-process recall (p99 2.8 ms)
63 ms
p50 same query, remote DB (p99 to 2 s)

Latency is why the data layer moved into the process. Once it is in there, the process has to scale — and that is a GIL problem.

The engine was multi-threaded. The process it lived in was not.
This is the honest "why". A chatbot is one request. An agent is a loop: plan, call a tool, read, call another tool, five to twenty times per turn, and most of those calls are data access. Recall over a memory table, a federated query that joins a lake file with a live database and whatever the last tool returned, a Python function inside that query to score or embed rows, and the result handed back as a DataFrame. We had already won the latency argument: in-process recall is p50 1.1 ms against 63 ms for the same query over the wire, with a p99 tail that reaches seconds when the network hiccups. Those are from our local-vs-remote benchmark, github.com/auxten/agent-local-vs-remote. But once everything runs inside one process, that process needs to use the machine. Sixteen engine threads were ready. The Python side was single-file. That is the itch.
Part 1 · Python 3.14t

What 3.14 changes — all the history you get today

PEP 703 → PEP 779

GIL optional since 3.13 (experimental). Officially supported in 3.14. Making it the default is a later phase.

A separate build

python3.14t, wheels tagged cp314t. Single-thread penalty ~5–10% (was ~40% in 3.13t).

The stack moved

61% of the top 360 compiled packages ship free-threaded wheels (Jul 2026). manylinux dropped 3.13t: 3.14t is the target.

$ python3.14t -c "import sys; print(sys._is_gil_enabled())"
False        # threads now run Python bytecode in parallel
How it stays fast: biased refcounting, immortal objects, per-object locks, lock-free dict/list reads.
What that costs you as an extension author: every borrowed reference and every global is now your problem.
One slide of context. The rest is engineering.
Deliberately one slide. PEP 703 made the GIL optional in 3.13 as an experiment; PEP 779 made it supported in 3.14. It is a separate interpreter binary, python3.14t, and a separate wheel tag, cp314t. The single-thread penalty came down from roughly 40 percent to 5 to 10, which is what made it usable. The ecosystem followed: as of July, 61 percent of the top 360 compiled packages ship free-threaded wheels, per hugovk's tracker, and manylinux dropped 3.13t, so 3.14t is the only free-threaded target worth building for. The engineering under it, biased refcounting, immortal objects, per-object locks, is why it is fast, and also why a borrowed reference that was harmless for thirty years is now a use-after-free. That is the whole history lesson.
Part 1 · The catch

Your extension gets nothing for free

One bad import poisons the well. Any extension that has not opted in makes CPython silently turn the GIL back on for the whole process.
"Thread-safe because GIL" is now a data race. Every global, cache and lazy init loses its silent protection.
Your abi3 wheel will not load. No stable ABI on 3.14t — new wheels, new CI lanes.
$ python3.14t -c "import _chdb"
RuntimeWarning: The global interpreter lock (GIL) has been enabled to load
module '_chdb', which has not declared that it can run safely without the GIL.

So the agent process above, with sixteen threads firing tool calls, was running exactly as serial as before on 3.14t — until the extension in the middle opted in.

Free-threading is opt-in, per extension module. This talk: what opting in took.
Three things bite extension authors. First, the silent re-enable: import one extension that has not declared itself safe and CPython turns the GIL back on for everyone, with a warning most people never read. Second, twenty years of code that was thread-safe only because the GIL serialized it. Third, the stable ABI does not exist on the free-threaded build, so your abi3 wheel is out; you build and ship cp314t wheels separately. The practical consequence for us: an agent process running sixteen tool calls on 3.14t got zero benefit, because our module was the undeclared import. That warning is us. Fixing it is the rest of the talk.

Part 2 · The toll gate

Parallel engine × serial glue = serial query

Python UDF calls

score(text, query) over every memory row: 16 streams, one gil_scoped_acquire, one thread at a time. Worse: it used to fork.

String-heavy columns

Agent memory is all strings: transcripts, tool logs, JSON. object-dtype = one PyObject per cell, read under the lock. 1.45 GB of one coding agent's JSONL was 213,721 rows of it.

DataFrame integration

Python(df) reads live pandas columns; results return as frames. NULL handling, dtype checks, pandas.NaT lookups: every one a Python call.

The GIL did not slow the engine down. It serialized every conversation with Python.
The picture: sixteen engine threads on the left, happily parallel, all queuing single-file at the GIL to reach three things on the right. Python UDFs: an agent that scores or embeds memory rows in Python calls back into the interpreter per row, and on a stock build sixteen streams take turns; before that, UDFs did not even run in-process, they forked, which we will get to. Strings: agent memory is text all the way down. Transcripts, tool output, JSON. We measured one laptop's Claude Code transcripts at 1.45 GB across 213,721 rows, and a pandas object column of that is one PyObject per cell, each read under the lock. And the DataFrame path, which is how results get back to the tool loop: NULL checks and dtype lookups that are each a tiny Python call. The engine was never the bottleneck. The border was.
Part 3 · Three changes
03

Three changes that unlocked parallelism

Restructure first, then remove the lock, then go low-level where the rows are.

12 min
01

Run Python UDFs in-process

Kill the subprocess pipeline before anything else.

02

Declare the module GIL-independent

Py_mod_gil — then survive the audit it implies.

03

Rework the string hot paths

Friendly Unicode APIs out; raw bytes and Arrow buffers in.

The meat, twelve minutes. Three changes in the order we made them, and the order matters: first restructure so that there is something for free-threading to speed up, then the one-line declaration and the audit behind it, then the string hot paths, which is where most of the bytes actually are.
Change 1 · UDFs

UDFs ran out of process

The old decorator wrote a script plus an XML config. The engine forked a Python interpreter and piped rows through it as text.

Fork + interpreter startup on the query path
Rows serialized as TabSeparated text over stdin/stdout
Every argument arrives as str — no types
No shared state with your process: the embedding model you already loaded? Loaded again, per fork.

The GIL was not even the bottleneck yet. The fork() was.

Change one, and it starts with an embarrassing admission. Our Python UDFs did not run in the process at all. The decorator generated a script and an XML file, the engine forked a fresh interpreter, and rows went through as tab-separated text. Every argument arrived as a string. And for the workload we care about this was fatal: a scoring or embedding UDF needs a model, and the model you had already loaded in the agent process was not there. It got loaded again, inside the fork, per query. Free-threading would have done nothing for this design. There was no Python in our process to parallelize. So step one had nothing to do with the GIL.
Change 1 · UDFs

After: native in-process UDFs

C++ holds your py::function and calls it from the engine pipeline. Typed args, shared state, zero subprocesses.

from chdb import func
from chdb.sqltypes import STRING, FLOAT64

@func([STRING, STRING], FLOAT64)   # in-process
def score(text, query):
    return reranker(text, query)   # model loaded once

sess.query("""
  SELECT text, score(text, 'S3 cost spike') AS s
  FROM memory WHERE user_id = 'u1'
  ORDER BY s DESC LIMIT 8""")
// C++: PythonScalarUDF::executeImpl
// called from engine worker threads
py::gil_scoped_acquire acquire;   // <-- THE lock

for (size_t row = 0; row < rows; ++row)
{
    py::tuple py_args = box_arguments(row);
    py::object out    = func(*py_args); // yours
    insert_into_column(result, out);
}

Faster already. But see that gil_scoped_acquire? On a stock build, every engine thread queues on it.

After: the decorator registers a real Python callable, C++ keeps a py::function, and the engine's worker threads call it with typed arguments. The example is the agent shape: a reranker scoring memory rows against the current question, using the model the process already has. No fork, no text protocol. Now look at the C++ on the right. One line, gil_scoped_acquire. Correct, necessary, and on a stock interpreter it is the toll gate: sixteen engine threads reach that line and take turns. We had moved the Python into the process precisely so that free-threading would have something to work on. Next slide is what happened when it did.
Change 1 · UDFs

This is what no-GIL was made for

Stock 3.14: 4M-row scalar UDF, 16 streams: ~0.85 s flat, threads or not.
3.14t: the same acquire is cheap: 0.72 → 0.15 s from 1 → 8 threads, holds at 32.
Your UDF must be thread-safe too: it now runs concurrently. A model call usually is; a Python dict cache is not.
Per-row boxing still costs: PyObject_Vectorcall + a reused arg frame cut it 4.7× (chdb-core#142).

16-core x86_64, best of 3, chdb-core 26.5.1 post-fix numbers.

Order matters: in-process first, then remove the GIL. A subprocess pipeline gains nothing from free-threading.
Amsterdam picture. Stock 3.14 is one bike lane: sixteen engine threads, one of them runs Python at a time, the rest queue. On the 4M-row scalar UDF that was a flat 0.85 seconds no matter how many threads we gave it. 3.14t gives every thread its own lane. Same C++, same gil_scoped_acquire, but on the free-threaded build that acquire is per-thread bookkeeping, not a global lock. 0.72 seconds on one thread down to 0.15 on eight, and it held at 32. Two caveats, both honest. Your UDF now runs concurrently, so it has to be thread-safe; a model forward pass usually is, a plain dict you use as a cache is not. And boxing arguments per row still costs; switching to PyObject_Vectorcall with a reused argument frame took 4.7x off that overhead, that is chdb-core PR 142. This benchmark UDF is trivial on purpose: it measures the calling floor under any real scoring function. TODO: measure the same curve with an actual reranker model if there is time before Thursday.
Change 2 · Opt in

Opting in: one line, and an audit

// pybind11
#ifdef CHDB_FREE_THREADING
PYBIND11_MODULE(_chdb, m, py::mod_gil_not_used())
#else
PYBIND11_MODULE(_chdb, m)
#endif
// raw C API — the same claim
static PyModuleDef_Slot slots[] = {
    {Py_mod_exec, mod_exec},
#ifdef Py_GIL_DISABLED
    {Py_mod_gil, Py_MOD_GIL_NOT_USED},
#endif
    {0, NULL}};

The line is easy. It is a claim about every global in your codebase. The real work was a state audit:

Import cache, UDF registry, engine singleton, dtype caches — every "thread-safe because GIL" spot got a real primitive: call_once, shared_mutex, PyMutex.
Borrowed → strong references on anything another thread can mutate: PyList_GetItem → PyList_GetItemRef.
Textbook C++ concurrency. The hard part is finding it, not fixing it. Our import cache's lock-free fast path had been a data race for years. The GIL was its alibi.
None of the fixes were exotic. The GIL was just hiding the to-do list.
Change two is one line in two dialects: py::mod_gil_not_used() in pybind11, or the Py_mod_gil slot with Py_MOD_GIL_NOT_USED in the raw C API. Note we only compile it in for the free-threaded build, because the free-threading build also forced us off the stable-ABI pybind11 fork and onto upstream pybind11, which is its own CI matrix. The line itself is a promise: nothing in this module relies on the GIL for correctness. Keeping that promise meant auditing every global. The import cache that resolves pandas and numpy types, the UDF registry, the engine singleton, the dtype caches. Each got a real primitive: call_once for one-shot init, shared_mutex where readers dominate, PyMutex where Python objects are involved. And borrowed references became strong ones wherever another thread could mutate the container underneath us. None of it is clever. The uncomfortable finding was that our import cache's supposedly lock-free fast path had been a race for years. The GIL had been covering for it.
Change 2 · Shared state

Shared state: fix the race, then the bug it was hiding

// PythonImporter::ImportCache() — on the per-row scan path
#ifdef CHDB_FREE_THREADING
  // A process-global mutex here would serialize every
  // scan thread once per row. call_once: one-shot init,
  // then a lock-free fast path. The initializer is pure
  // C++, no Python calls: it cannot recurse or block.
  static std::once_flag init_flag;
  std::call_once(init_flag, [] {
      cache = std::make_shared<ImportCache>();
  });
#else
  // Stock build: the GIL already serializes callers.
  if (!cache)
      cache = std::make_shared<ImportCache>();
#endif
  return *cache;

The nastiest bug: lazy init on a GIL-free thread

Trigger. First NULL in a string column — a tool result with a missing field — makes a scan thread lazily import pandas.NaT. With no Python thread state.

Crash. Segfault deep inside the allocator, nowhere near the actual bug.

Hang. Then the fatal-signal handler deadlocks. No traceback, no exit. The query just hangs, forever.

Fix: two lines. Resolve everything eagerly, while you still hold the GIL. Finding it took days.

Debugging silence is the expensive part. Budget for it.
Left is the actual code from the import cache, because it shows the trade-off. This function sits on the per-row scan path. A global mutex would have been correct and would have serialized every scan thread once per row, which defeats the point. call_once gives a one-shot init and a lock-free read afterwards, and the comment matters: the initializer is pure C++, no Python calls, so it cannot recurse into the interpreter or block on a lock it is holding. Right is the bug that fixing the race exposed. First NULL in a string column, which in agent data is every other row, a tool result with a missing field. A scan thread lazily imports pandas.NaT, from a thread that has no Python thread state. Segfault inside the allocator, nowhere near the cause. Then the fatal-signal handler deadlocks, so no traceback, no exit, the query just hangs. The fix was two lines: resolve those attributes eagerly at import time, while you hold the GIL. Finding it was days. Free-threading bugs do not crash loudly; they go quiet.
Change 3 · Strings

Strings are the hot path: go straight to the bytes

Millions of strings cross the C++/Python border per query, and for a memory table they are the data. Friendly Unicode APIs cost a call per value. On 3.14t we read CPython's memory directly:

// FillColumnString — free-threaded build
if (PyUnicode_IS_COMPACT_ASCII(obj)) {                    // most logs, ids, JSON keys
    data = (const char *) PyUnicode_1BYTE_DATA(obj);      // direct pointer, no copy
    len  = PyUnicode_GET_LENGTH(obj);
}
else if (auto * u = (PyCompactUnicodeObject *) obj; u->utf8) {
    data = u->utf8;  len = u->utf8_length;                // cached UTF-8, still no copy
}
// ...compact 1/2/4-byte kinds transcoded; legacy fallback omitted
ASCII string → a pointer read. No shim, no allocation, safe from any thread because a str is immutable.
Free-threaded builds cannot use the stable ABI anyway. The non_limited_api wrappers went; nothing left to lose by going low-level.
Rule of thumb on hot paths: the friendlier the API, the more it costs per row.
Change three, strings. For a memory table or a transcript log, strings are not metadata, they are the payload. Every one crossed the border through a pybind11 shim and a friendly Unicode API, one call per value, and each call touched the interpreter. The free-threaded build cannot use the stable ABI at all, which turned out to be liberating: we replaced the limited-API wrappers with direct CPython calls. If the string is compact ASCII, which most logs, identifiers and JSON keys are, it is a pointer and a length; no copy. If CPython already cached a UTF-8 representation, we use that; still no copy. Only the 2- and 4-byte kinds get transcoded. A str is immutable, so reading its buffer from any engine thread is safe without a lock. This is the actual code from FillColumnString under CHDB_FREE_THREADING, slightly compressed.
Change 3 · Strings

The biggest win: skip PyObject entirely

pandas 3.x str columns are Arrow-backed: plain C buffers, scanned directly on all streams, no GIL at all.

object dtype (before) — 219.2 s
Arrow zero-copy (after) — 20.1 s

ClickBench, 50M-row hits DataFrame, all queries, pandas 3.x, hot run · 10.9× total · geomean 4.5× · string-heavy queries up to 64×

Priority on hot paths: no PyObject > cheap PyObject access > friendly PyObject APIs.
And then the biggest single win had nothing to do with locks. pandas 3 makes string columns Arrow-backed by default: a validity bitmap, an offsets array and one contiguous data buffer. Those are plain C memory. Every engine stream can read them directly, zero-copy, and no thread ever touches a PyObject. ClickBench on a 50-million-row hits DataFrame went from 219 seconds to 20; string-heavy queries up to 64 times. So the ranking on a hot path is: avoid Python objects entirely if the data layout lets you; if not, read them as cheaply as CPython allows; and use the friendly APIs only where the row count is small. Free-threading fixes the middle tier. Zero-copy removes the tier.

Part 4 · Scar tissue

What broke, what surprised us

The silent GIL re-enable got us too. One undeclared dependency in the agent's environment and our "no-GIL benchmark" was measuring the GIL.
Crashes hide as hangs. Allocator segfault → signal-handler deadlock. In a long-running agent that is a tool call that never returns.
Stable ABI: gone. No abi3 on 3.14t → upstream pybind11, direct CPython calls, separate cp314t lanes. The CI matrix doubled.
Cold start + many threads hung. Fresh 3.14t process, first UDF at max_threads=32: GC's stop-the-world deadlocked against an import-cache call_once (chdb-core#131). Fix: detach before you block.
Per-row tuples fed GC storms. UDF throughput collapsed past 8 threads until the arg frame was reused (chdb-core#128). Free-threaded GC is more sensitive to allocation churn, not less.
Free-threading did not create these bugs. It revoked the amnesty.
Five scars. The silent re-enable got us: an agent environment has dozens of compiled dependencies, one of them had not opted in, and our first "free-threaded" benchmark was quietly measuring the GIL. Crashes turning into hangs is worse in an agent than in a script, because a hung tool call looks like a slow model. The stable ABI going away was the biggest structural cost: upstream pybind11 for the free-threaded build, direct CPython calls, doubled CI. Then two we found only by benchmarking. A cold process with a high thread count hung on the first UDF: the free-threaded GC stops the world, and one of our threads was blocked inside a call_once while still attached, so the stop never completed; the fix is to detach from the interpreter before blocking on anything. And UDF throughput collapsed past eight threads because per-row argument tuples were feeding GC storms; reusing the argument frame fixed it. Both are fixed in 26.5.1. That is what benchmarks are for.
Part 4 · Decision guide

Where no-GIL did not help, and where it did

No gain when…

Your C++ already releases the GIL for the heavy work. The pure-engine query stayed at parity (0.161 s).
You can avoid Python objects entirely (Arrow, buffers, NumPy). Zero-copy beat lock-removal.
The workload is single-threaded. You pay ~5–10% for nothing.

Real gain when…

Many threads must execute Python: UDFs, callbacks, the scoring function inside the query.
Many threads must read PyObjects: object-dtype columns, tool results as they arrive.
Many concurrent callers in one process — the tool loop — and the GIL was your measured bottleneck.
Zero-copy beat lock-removal. Free-threading fixes what zero-copy cannot reach: running actual Python in parallel.
Be fair about it. Anything that already ran outside the GIL did not get faster: the pure-engine query, no Python objects involved, was 0.161 seconds on both builds. Anything we could make zero-copy got faster without free-threading, and got more from that than from the lock going away. And a single-threaded workload pays the 5 to 10 percent tax for nothing. Where it paid: whenever many threads have to run Python or read Python objects. The scoring UDF in the query. The object column of tool output. And the case that started all this: many callers in one process, each holding Python state, each wanting the engine now. That was our measured bottleneck, not a hunch.

Part 5 · What it unlocks

What this buys: one process, no worker pool

sess = chdb.session.Session("./brain")          # memory + traces, local

@func([STRING, STRING], FLOAT64)
def score(text, q): return reranker(text, q)     # one model, all threads

def recall(user, q, q_vec):                      # one tool call
    return sess.query(f"""
      SELECT m.text, score(m.text, '{q}') AS s, e.last_seen
      FROM memory m
      JOIN s3('s3://lake/events/*.parquet') e USING (user_id)    -- the lake
      JOIN postgresql('rds:5432','crm','users') u USING (user_id) -- live DB
      WHERE m.user_id = '{user}' AND m.ts > now() - INTERVAL 30 DAY
      ORDER BY cosineDistance(m.emb, {q_vec}) LIMIT 8""", "DataFrame")

with ThreadPoolExecutor(16) as pool:             # 16 tool calls in flight
    frames = pool.map(lambda r: recall(*r), requests)
One model in memory, not 16 workers × 16 copies. The UDF sees the process's objects.
No pickle, no IPC. Results come back as frames in the calling thread.
Engine threads and Python threads share the cores instead of taking turns at a lock.
If the process is disposable (Lambda, a MicroVM, a sandbox), the table can flush to a bucket and be reopened elsewhere. Different talk.
Sixteen tool calls, one interpreter, zero subprocesses.
This is the shape we were after, and it only works on 3.14t. One process holds the memory table and the traces as local tables, one reranker loaded once, and a thread pool of tool calls. Each call is one SQL statement: rank the user's recent memories by vector distance, score them with the Python function, and join in the lake file and the live CRM table for context, returned as a DataFrame. Sixteen of those in flight. On stock Python the pool would be theatre: the UDF, the string columns and the DataFrame conversion all funnel through one lock. On 3.14t the engine threads and the Python threads share the cores. No worker processes, so one copy of the model, no pickling results across a pipe. The last bullet is a pointer, not a pitch: when the process itself is disposable, a Lambda or a sandbox, the local tables can flush to object storage and be reopened on the next host. That is its own talk; the point here is only that the state and the compute now fit in one process that can use the whole machine. To be clear, this slide is a sketch of the pattern, not a benchmark; the measured numbers are the previous slide and the TODO in its notes.
Part 5 · Checklist

Porting checklist for extension authors

Measure first. Is the GIL your bottleneck, or a hunch? Count threads waiting on it under real load.
Restructure before you parallelize. In-process before parallel; zero-copy (Arrow, buffers) before lock-free.
Declare it. Py_mod_gil / py::mod_gil_not_used() / Cython freethreading_compatible=True. No abi3 on 3.14t.
Audit every global. Caches, registries, singletons, lazy init → PyMutex, call_once, shared_mutex.
Borrowed → strong refs where another thread can mutate: PyList_GetItemRef, PyDict_GetItemRef.
Resolve imports eagerly, while you hold the GIL. Never lazily from an engine thread.
Detach before you block. Release the thread state before waiting on a lock or condvar, or stop-the-world GC deadlocks you.
Cut per-row PyObject churn. Vectorcall, reused arg frames. Per-row tuples = GC storms past ~8 threads.
Verify at runtime. sys._is_gil_enabled() in tests; treat the RuntimeWarning as a failure. One dep re-enables the GIL.
CI: separate cp314t lanes, full suite under PYTHON_GIL=0, and a cold-process, high-thread stress case.

The list I wish I had. Yellow, before you touch code: measure whether the GIL is actually the bottleneck, and restructure first, because in-process and zero-copy each gave us more than the lock did. Blue, the port itself: declare it, audit every global, turn borrowed references into strong ones where another thread can mutate the container, resolve imports eagerly, detach before blocking, and stop allocating per row. Green, verification: check sys._is_gil_enabled() in your tests and fail on the warning, because one dependency silently reverts everything; and give CI a cold-process, high-thread case, because that is where our two nastiest bugs lived. The long version of all of this is the py-free-threading guide; this is the part we personally bled on.

Three takeaways

01

Restructure before you parallelize.

In-process beats out-of-process; zero-copy beats lock-free; then free-threading multiplies what is left.

02

The GIL was an amnesty, not a feature.

3.14t revokes it. The bugs it exposes were already yours.

03

One process can now use the machine.

Memory, federation and Python scoring from sixteen threads, no worker pool. That is what the port was for.
