Porting a C++ Python extension to free-threaded Python 3.14

Auxten Wang · Technical Director @ ClickHouse · Creator of chDB

One story. What it took to make a C++ extension faster on free-threaded Python, and what we measured at the end. The workload that hurt us was many concurrent queries from one Python process, most of them coming out of our own agent tool loops. The GIL sat in the middle of every one of them. Every core, one process, no worker pool: that is the target. Numbers at the end.

The problem

A parallel engine, one lane into Python.

Part one, the problem. What chDB is, exactly where the GIL bit it, why the usual workarounds did not apply, and why the agent era made it urgent.
chDB

chDB: the ClickHouse engine inside your Python process

pip install chdb

sess = chdb.session.Session("./brain")
sess.query("""
  SELECT m.text FROM memory m
  JOIN s3('s3://lake/events/*.parquet') e USING (user_id)
  JOIN Python(tickets) t USING (user_id)
  WHERE m.user_id = 'u1' LIMIT 8""")
For those who do not know ClickHouse: the open-source columnar analytics database. chDB is that whole engine as a pip install, living inside your Python process, no server. Local tables on disk, files on S3, a Postgres table, a live DataFrame: all tables in one statement. That is all the ClickHouse you need for this talk. What matters: the engine is heavily multi-threaded C++, glued to Python by pybind11, and it calls into Python in two places that hurt: user-defined functions and strings.
Bottleneck 1

A multi-threaded engine calling a Python function: every thread waits for one lock.

Here is the mechanism. ClickHouse's query engine is multi-threaded: N worker threads, each processing its own block of rows, in parallel. The moment the SQL calls a Python function, every one of those threads has to call into Python, and every call has to take the GIL. So N parallel engine threads collapse into a queue at one lock. This is structural, not a bug: the function is Python, so it cannot release the GIL the way NumPy's C loops do. We measured a scalar UDF over four million rows on a 16-core box: about 0.85 seconds with one engine thread, with eight, with thirty-two. Flat. The engine scaled; the lock did not.
Bottleneck 2

A string column is one Python object per cell. Reading a cell takes the lock.

Second place, same mechanism. Agent memory is text all the way down: chat logs, tool output, JSON. In pandas an object column is one Python object per cell, and reading a Python object means taking the lock. So the engine threads on the left queue at the same padlock to read cells on the right. Our scan of five million such strings with 16 engine threads: 0.22 seconds on stock 3.14. On stock, adding threads to this scan made it slower; we do not have a clean per-thread-count series to show, so I will only compare like for like later. Everything I said about strings applies to any object-dtype DataFrame crossing into or out of the engine.

Workarounds

Every workaround assumes Python is at the edge. Ours is in the middle.

Bottleneck 1 · a Python function per row

Release? The callback is Python.
Compile away? It is the user's function.
Batch? SQL calls it row by row.
Process pool? Copy every block out, load the model per worker.

Bottleneck 2 · string columns

Release? One PyObject per cell; every read takes the lock.
Vectorize? The cells are not a buffer, they are objects.
Another process? Pickling five million strings costs more than the scan.
Hold the table against our two problems. The function per row: release the GIL inside the loop? The loop calls back into Python per row; the work is Python. Compile it away? It is the user's function, written this morning. Batch? SQL calls a scalar function per row. A process pool? Every block copied out of the engine, the user's model loaded again in every worker. Strings: a Python string is an object, not a buffer; reading it is a lock operation, and pickling five million of them costs more than the scan. The table works when Python coordinates from the edge. In chDB the engine coordinates and Python is in the middle of the hot loop.
Agents

One agent turn: six Python steps, one lock

This is any Python agent, one loop iteration. The turn fans out: call an external API, read the session history, load context from files or a vector store, run a tool function, compute an embedding or rerank, write the result back to memory. The shape everyone builds: asyncio handles the waiting, threads were supposed to handle the rest. The I/O steps do release the GIL while blocked. The CPU steps do not, and every step still takes the lock to touch the dicts, lists and strings it passes to the next one. So "the rest" runs sequentially: a concurrent tool loop executes one step at a time. Our chDB tool call was just one of these steps.
Agents

So the GIL shapes how Python builds agents

A process pool per tool — pickle every dict across
Memory in a remote service — a network hop per step
Logic out of Python — Rust or Go sidecars
Look at how agent stacks are built and you see the lock in the architecture. Three escape routes. Tools run in a process pool: every dict pickled across, a model per worker. Memory and retrieval move to a remote service: a network hop per step. One data point, with its conditions: the same recall query, p95 of 1.7 milliseconds in-process versus 93 milliseconds over a network with half a percent packet loss, on our test rig. Or the logic leaves Python for a Rust or Go sidecar. None of these are wrong; they are what you do when one interpreter runs one thread. A diagnosis, not a complaint.

What we did

What finally changed, and the two steps we took with it.

What changed

Removing the GIL: 29 years of tries

Thirty seconds of history, because it explains the tax. The yardstick is Guido's, from 2007: he would take GIL removal only if single-threaded programs did not get slower. Every attempt here was measured against that sentence. 1996: Greg Stein removed the GIL from Python 1.4 with fine-grained locks. It worked, and single-threaded code ran nearly twice as slow, so it died. 2009: Antoine Pitrou rewrote the GIL for 3.2: fairer scheduling, same lock. 2016: Larry Hastings' Gilectomy; every refcount became an atomic operation, the interpreter crawled, abandoned. 2017 on: Eric Snow gave each sub-interpreter its own GIL in 3.12. A sidestep, not a removal. 2021: Sam Gross's nogil branch solved the refcount problem with biased reference counting and immortal objects, kept single-thread speed within a few percent, and became PEP 703. Every failure was the same failure: single-thread speed. Next: how the last one got under the bar.
What changed

Why nogil passed: no big trick, four small ones

Biased refcounting

Owner counts without atomics.

Immortal objects

Never refcounted at all.

Deferred refcounting

Stack refs skipped; GC checks.

Per-object locks

One tiny lock per container.

Result: ~1–8% single-thread cost. Guido's rule, met.

Not one big idea: a stack of small ones, each avoiding shared memory. Biased reference counting: every object remembers its creating thread; that thread bumps a plain counter, everyone else uses a second, atomic one. Immortal objects: None, True, small integers and interned strings are never counted at all, so the hottest objects are never contended. Deferred reference counting: functions, modules and code objects are pushed and popped constantly; the interpreter skips those counts and the cycle collector settles up. Per-object locks: a one-byte lock in every list and dict, reads mostly lock-free, writes take that object's lock only. Together: a few percent single-thread cost, under Guido's bar. And that is the tool we picked up.
Step 1 · Flip the switch

One line, one promise: nothing here needs the GIL

// pybind11 ≥ 2.13
PYBIND11_MODULE(_chdb, m,
    py::mod_gil_not_used())
Step one is one line; the raw C API has the same slot, Py_mod_gil. The line is a promise: nothing in this module relies on the GIL for correctness. Keeping it meant auditing every global: the type cache, the UDF registry, the engine singleton. Each needed a real lock. Borrowed references, pointers you do not own, became strong ones wherever another thread could mutate the container underneath us. And the engine threads call your Python callable directly, each taking its own acquire. None of it is clever. The GIL had just been hiding the to-do list.
Step 1 · Flip the switch

Our import cache raced for years. The GIL was its alibi.

First NULL → a lazy import
Segfault, far from the bug
Then a hang. No traceback.
The human beat. Our import cache, the thing that resolves pandas and numpy types, had a lock-free fast path that had been a race for years. The GIL was its alibi. We fixed the race with a one-shot initialiser, and that exposed the bug it had been hiding. First NULL in a string column, and a scan thread lazily imports pandas.NaT from a thread that was not attached to the interpreter. Segfault inside the allocator, nowhere near the cause. Then the crash handler deadlocks: no traceback, no exit, the query just hangs. The fix was two lines, resolve those attributes eagerly at module init. Finding it took days. Free-threading bugs do not crash loudly. They go quiet.
Step 1 · Result

Same UDF, 8 threads: 0.85 s → 0.15 s

And the number, after the switch. Stock 3.14 is one bike lane: many engine threads, one of them runs Python at a time, so the number does not move with thread count, about 0.85 seconds. 3.14t gives every thread its own lane: one thread 0.72 seconds, eight threads 0.15, flat to 32. Same C++, same acquire; on 3.14t that acquire is per-thread bookkeeping, not a global lock. One reading caveat: 0.85 is the contended number, so do not read 0.85 against 0.72 as the single-thread tax; that is a different measurement. One obligation: your UDF now runs concurrently, so it has to be thread-safe. A dict used as a cache still races on "if key not in cache, compute and store".
Step 2 · Strings

Strings: go straight to the bytes

// FillColumnString, free-threaded build
if (PyUnicode_IS_COMPACT_ASCII(obj)) {         // logs, ids, keys
    data = (const char *) PyUnicode_1BYTE_DATA(obj);  // no copy
    len  = PyUnicode_GET_LENGTH(obj);
} else {
    data = PyUnicode_AsUTF8AndSize(obj, &len);  // thread-safe
}
Step two, the string path. Millions of strings cross the border per query, and each went through a pybind11 shim and a friendly Unicode API, one call per value. The free-threaded build cannot use the stable ABI anyway, so nothing was lost by going low-level: direct CPython calls. Compact ASCII, which most logs, identifiers and JSON keys are, is a pointer and a length, no copy, and that buffer is immutable, so any engine thread may read it. Everything else goes through PyUnicode_AsUTF8AndSize, the public call. We first read CPython's cached UTF-8 field directly; that field is filled lazily and reading it from another thread is a data race on 3.14t. The public call handles that.

And then the biggest single win, which was not the lock. pandas 3 with PyArrow stores string columns the way Parquet does: a validity bitmap, an offsets array, one contiguous buffer. Every engine thread reads that directly, zero-copy, and no thread touches a Python object. ClickBench on a 50-million-row DataFrame, 43 queries: 219 seconds down to 20, 10.9 times less total time; geometric mean 4.5, string-heavy queries up to 64 times. This needs no free-threading. It works on the Python you have today. The ranking on a hot path: avoid Python objects if the layout lets you; free-threading is for the ones you cannot avoid.

Looking back

Agent tool calls and pandas jobs, one process

Looking back, this is what the port bought. One process. Agent tool calls come in on the left, a recall query with a Python reranker inside it. pandas jobs come in next to them, a Parquet aggregation over S3. The engine serves them on its own threads, and the Python parts run in parallel too. One copy of the model, loaded once. No worker pool, no pickling, no remote memory service on the hot path. Sketch, for the notes reader: a @func score(text, q); recall(user, q) runs one SQL with score inside; report(day) is a chdb.datastore chain over Parquet; both go to one ThreadPoolExecutor. A sketch, not a benchmark.
Looking back

A pandas chain becomes one SQL query

import chdb.datastore as pd
df = pd.read_parquet("events.parquet")
top = (df[df.status == 200]
         .groupby("user_id").amount.sum()
         .sort_values(ascending=False)
         .head(10))
SELECT user_id, sum(amount) AS amount
FROM file('events.parquet')
WHERE status = 200
GROUP BY user_id
ORDER BY amount DESC
LIMIT 10

One compiler

Ten chained ops → one plan. No intermediate copies.

Every core

pandas computes on one core. The engine fills them all.

Streaming

Top-10 of 10M rows keeps a 10-row heap, never the sorted table.

The pandas side of the same story. chdb.datastore is a pandas-compatible layer that ships with chDB: change the import, keep the code. Every call is recorded into a lazy chain; when you ask for a result, a compiler rewrites the whole chain into one SQL statement for the engine, and anything it cannot translate falls back to real pandas mid-pipeline. Three reasons that is faster. One plan instead of one materialized copy per step. Every core instead of one. And streaming: a top-10 over ten million rows keeps a ten-row heap instead of sorting the table, which is why sorts are the blowout on the next slide.

Design argument, not measured

With the GIL off, .map(python_fn) inside that chain runs as an in-process UDF on every engine thread.

Measured on one laptop for PyCon JP: a 10-million-row Parquet, read to answer, best of two, outputs identical on every op. Log scale. Sorts are the blowout, 35 to 52 times, because of that heap. Filters and chains, 3 to 22 times. Where pandas wins: bulk value replace, which pandas does in place and we round-trip through the engine, and simple groupby-count shapes. Keep pandas there. Peak RSS median: 1,059 megabytes down to 440. The crossover: pandas faster at a hundred thousand rows, even near a million, 28 times at ten million, 52.7 on the published 100-million-row ClickBench total. The orange card is the tie to this talk, a design argument, not a measurement: with the GIL off, a Python .map inside that chain runs as an in-process UDF on every engine thread.

One undeclared import re-locks the whole process

$ python3.14t -c "import yourstack"
RuntimeWarning: The global interpreter lock (GIL) has been enabled
  to load module 'X', which has not declared that it can run safely

PEP 779: supported, not default

3.14t is an official build with the same release cadence. You install it on purpose.

The tell, and the override

The warning names the package. PYTHON_GIL=0 forces the GIL off and silences it: check first, force second.

Why your report matters

Free-threading is a per-process property decided by the weakest dependency. One issue on that package unblocks everyone above it.

Why the holdouts matter more than the percentage. Import one extension that has not declared itself safe and CPython turns the GIL back on for the whole process, with this warning. Your other forty packages did the work and get nothing. PEP 779 made 3.14t supported rather than experimental: an official build on the normal release cadence, but not the default; you install it on purpose. The warning names the package that re-locked you. PYTHON_GIL=0 forces the GIL off anyway, which is useful for testing and dangerous in production because it silences the warning. So: check first, force second. And this is why one issue filed against that one package matters: free-threading is a per-process property decided by your weakest dependency.
