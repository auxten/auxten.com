Why a compatibility layer instead of a better API

Programming now has a BC and an AD.

Before ChatGPT

Fifteen years of humans writing pandas by hand, in public.

  • Millions of notebooks and Stack Overflow answers
  • Every data-science course, book, and blog
  • Clean. Not one line of it generated by a model.
30 NOV
2022

After ChatGPT

Models trained on that corpus treat it as how the world is.

  • Ask any model for data code: you get pandas
  • Ask it for a groupby: you get .groupby().agg()
  • The API stopped being a library. It became a fact.

pandas is the de facto standard — the way the Gregorian calendar is: not the best design, just the one everyone counts in.

This is the reasoning behind the whole project. Everything written before late 2022 is a clean human corpus. Every large model learned data work from it, and in that corpus, data work means pandas. So pandas is no longer just a popular library; it is what the models believe data code looks like. You do not get to argue with that. You build on it.
The decision

Do not invent a new API in 2026.

Humans Agents are too lazy to learn.

A new API means fighting the model's prior on every single line it writes. A compatible API means every agent on earth is already fluent in your product.

The API is the asset. Replace the engine.

We used to say humans are too lazy to learn a new API, and that was true. Now the more important statement is that agents are too lazy to learn, in a very literal sense: they will keep writing what the training data taught them. If your API is different, you pay for that on every line, forever. So we kept the API and swapped the engine.
Our unfair advantage

We had a reference implementation.

Most AI-built projects have no way to know if the output is right. We did: pandas itself.

Every pandas behavior became a test we did not have to design.The agent writes the mirror. pandas is the judge. Neither one gets to grade its own work.
This is the single most important thing about how the project worked. We never asked the model whether its implementation was correct. We took real notebooks, swapped the import, ran both paths, and compared the full output: values, types, and row order. Pandas was the oracle. This made the whole thing verifiable from day one.
The rule we still follow

Read every thought.
Align hard, early.

In the first weeks I read the agent's reasoning for every change, not just the diff. When it reasoned wrong, I wrote the rule down that same day.

That is expensive. It is also the only time the rules are cheap to find.

WHAT WENT INTO THE RULES FILE IN MONTH ONE

All four rules are in the repository today: chdb-io/chdb · AGENTS.md
Be concrete. These four rules are real, they are in AGENTS.md in the public repository, and every one of them exists because I watched the agent reason its way to a wrong answer. The lazy-execution rule came from the agent eagerly materializing frames. The mirror-test rule came from tests that only checked one side. The early weeks are when you can still see the mistakes forming.
The shortcut we banned

Agents cheat.

A test fails because the rows come back in a different order. The fastest way to green?

the tempting “fix”
actual.sort_values(...)
expected.sort_values(...)
assert_equal(actual, expected)  # passes

Test green. Incompatible behavior now invisible.

AGENTS.md · verbatim
## 4. Testing principles

Using reset_index() in tests to mask
problems = DataStore bug, not correct
test writing.

FORBIDDEN:
❌ Only verifying len() without values
❌ Comments describing expected behaviour
   without actual assertions
❌ # TODO: verify later

REQUIRED:
✓ Complete output comparison
   (columns + data + order)
Agents optimize for the signal you give them. If the signal is "make the test pass," they will happily change the test. We caught sorting before comparison, reset_index to hide index bugs, and length-only checks. The right side is the actual text from our AGENTS.md. Observe the shortcut, then close it in writing where the next agent will read it.

This is the problem that nobody plans for. Working alone with agents, you accumulate rules very fast, and almost none of them get written down, because the agent you are talking to already knows them. Then a second person arrives with a second agent, and it is December again. The failure is not the new engineer. It is that the knowledge had no durable home.
Fix 1 · Code review

Reviewers with zero memory.

We added several review agents to the pull-request flow. On purpose, they know nothing about the project except the rules file.

The daily agent

Knows the history and every workaround. Eventually learns to step around every rough edge—just like I did.

The fresh reviewer

No project context. Told to be critical, rational, and evidence-driven. Checks the FORBIDDEN list on every diff.

In its first pass, a reviewer with no history flagged a masked test, an inconsistent method signature, and three undocumented behaviors—all things the two of us had stopped seeing.Creators and reviewers need different context. That is true for people, and it turned out to be true for agents.
The first fix was cheap: separate the roles. The agent that writes the code and I share the same blind spots. A reviewer that starts from zero, with only the rules file, sees what insiders stop seeing. This is not clever prompting. It is separation of duties, the same thing every engineering organization already does with people.
Fix 2 · The deeper problem

Most rules are born inside a decision.
Nobody notices.

In a review I say: “keep pandas' exact error message here.” That is a project rule. I did not think of it as one. Neither did the agent.

The agent understood it for that session. Then the session ended, and so did the rule.

ONE AFTERNOON OF REVIEW, THREE RULES NOBODY WROTE DOWN

“Match pandas' error text, not just the exception type.”

→ project rule

“Don't add a fast path here; the SQL builder should handle it.”

→ architecture decision

“We reproduce this pandas quirk on purpose.”

→ the kind of fact a new teammate “fixes” by accident

This is the pain that led to the tool on the next slide. Rules do not arrive labeled as rules. They arrive as small decisions in the middle of doing something else. The agent picks them up in the moment, and then they evaporate at the end of the session. Writing docs after the fact does not work, because you cannot remember what you decided in passing.

Explicit, not everything

The agent commits refined decisions and rules. Raw chat stays cold. No background mining of transcripts into “insights.”

Scoped

Every memory carries a project and a kind: principle, decision, fact. A rule for DataStore does not leak into another repo.

Shared

One local server on my Mac mini serves my laptop and my agents. Teammates point at the same store; ClickHouse backend when it outgrows one box.

github.com/auxten/clickmem · built on chDB · adapters for Claude Code, Cursor, Codex, Aider, Cline, Windsurf, Zed, Hermes and a generic REST/MCP path
ClickMem is what we built for this, on top of chDB. Hooks go into every agent we use. At the end of a session the agent, with its own model, decides which conclusions are worth keeping and commits them as structured rows: project, kind, tags, embedding. Next session, on any machine, the agent recalls by project and task. It is deliberately not a firehose: raw transcripts are stored cold and never injected. Only refined decisions enter the store.
Why a database, not a Markdown file

Recall is one SQL query.

Meaning, project scope, recency, and what helped before—one table, one round-trip, about 10 ms locally.

A Markdown memory file is write-only: it grows forever, every line competes for attention, and nothing expires. Rows can be filtered, ranked, revised, and audited.

recall.sql · the shape of it
SELECT content,
  1 - cosineDistance(embedding, :q) AS meaning
-- vector
FROM memory
WHERE project = 'chdb-io/chdb'
-- whose memory
  AND hasAny(tags, ['testing'])
-- keywords
  AND created > now() - INTERVAL 90 DAY
-- time decay
ORDER BY pinned DESC,
         meaning DESC,
         times_used DESC
-- past use
LIMIT 8
Simplified from ClickMem's recall. Production adds privacy filters, conflict status, and latest-version-only.
This is why memory is a database problem and not a file problem. One query does four jobs: cosineDistance ranks by meaning, WHERE keeps other projects out, the interval keeps a one-week workaround from becoming a permanent belief, and times_used is the cheap feedback signal. chDB runs this in-process in about ten milliseconds. The same SQL runs on a ClickHouse cluster when the team outgrows one machine.
The same idea, from someone else

Hermes Agent turns conversations into skills.

I use Hermes Agent for a lot of my daily operations. Its best feature: after a task, it writes what it learned into a reusable skill file, without being asked.

They call it self-evolving. It is less magical than that. It is a hook that turns a conversation into a file the next session will read.

That is exactly the right design. Whatever agent you run, this is the pattern to demand from it.

Give credit where it is due. Hermes Agent, which I use for a lot of my own operations, has a built-in loop where the agent updates its own skill files after a task. The marketing word is self-evolving. The engineering reality is a hook plus a file. That is fine, because the design is right: the conversation produces a durable artifact the next session reads. The Auto Loop

Agents that find their own edge cases.

A Python supervisor runs four agents in a loop. Files on disk are the shared state. Decisions are JSON, not prose.

1
Generator picks a real notebook, writes mirror tests
2
Implementer fixes whatever diverges from pandas
3
Runner executes the full suite
4
Reviewer returns APPROVE / IMPROVE / REJECT — then a PR, or a git rollback

Before the numbers · how it actually runs

Lazy chain → compiler → segments.

Segments run in order and pass results along. What comes back is a normal pandas DataFrame, same dtypes and index. A pandas segment mid-chain costs a round-trip through the engine—that is exactly where the next slide shows pandas winning.

One slide on how it works so the numbers make sense. Left: your pandas code, unchanged except the import. Every call is recorded into a lazy chain; nothing runs. When you look at the result, the compiler builds one plan and cuts it into segments. Three kinds: most ops have a SQL equivalent and become one statement for the ClickHouse engine. A map or apply with a Python function becomes SQL plus an in-process UDF. Ops with no SQL translation, like mask and where, become a pandas segment: real pandas runs that step and hands the result back. Hold on to the segment idea; it explains both the wins and the losses on the next slide.

Now the muscle slide. Ten million rows, twenty everyday operations, same laptop: DataStore wins fourteen. Sorts are the blowout, thirty-five to fifty-two times, because the engine keeps a ten-row heap instead of materializing the sorted frame. Peak memory is about a third of pandas. On the published ClickBench DataFrame benchmark the gap is seventy-one times overall. And the user changed one line.
Where pandas still wins

Six of twenty. We say so in the docs.

Small data

Under about a million rows, pandas is faster. Compiling to SQL has a fixed cost. Keep pandas there.

Bulk value replace

mask / where rewrite a column in place. We round-trip it through the engine. pandas wins on speed and RAM.

Anything we can't translate

Falls back to real pandas for that step. Correct, but no speedup. The logs tell you exactly which step.

The oracle that made the project possible also makes it impossible to hide this. Every benchmark row is a mirror test.
One clean concession, said out loud. Small data is pandas country. Bulk value replacement is pandas country. And anything the compiler cannot translate runs as real pandas, correct but not faster. The point for this room: because every result is compared against pandas, we could not oversell this even if we wanted to.

Read down the left column, then the right. One: ride the standard the models already know. Two: an external oracle. Three: watch the reasoning while it is cheap to correct, and ask whether you were wrong or unclear. Four: bans, not pleas; XFAIL, never a silent skip. Five: the rules file is the team interface, and every new line costs attention, so prune it. Six: a reviewer with no history, told to be critical and rational. Seven: files and JSON, not chat history, for multi-agent control. Eight: capture decisions at the end of the session and share them, because that is where rules are actually born. Nine: failures become permanent tests and the loop hunts the next one. Ten: the moat is the system around the model, not the prompt.
