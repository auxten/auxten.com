DataStore: One-Line Pandas Swap


import chdb.datastore as pd  # <- one line!

df = pd.read_csv("employee_data.csv")
filtered = df[
    (df['age'] > 25) &
    (df['salary'] > 50000)
]
grouped = filtered.groupby('city')['salary'] \
    .agg(['mean', 'sum', 'count'])
result = grouped.sort_values(
    'mean', ascending=False
).head(10)

Same Pandas API. Compiled to ClickHouse SQL underneath.

  • Lazy — every call returns a LazyOp; nothing runs until print(), len(), .columns
  • Pushdown — predicate, column pruning, limit propagation — automatic
  • Segment execution — chDB does what it can, Pandas handles the rest, handoff via memoryview
  • Unified sources — local files, S3, PostgreSQL, in-memory DataFrame — same pipeline

Python 3.14 Free-Threading: The Opportunity

Free-threaded Python lets threads run Python code in parallel — but C/C++ extensions do not benefit automatically. Authors must opt in, remove hidden GIL assumptions, and audit shared state.

chDB embeds a multi-threaded C++ engine. Several Python interactions still serialized execution: UDF calls, DataFrame column access, large numbers of strings.

Three Changes That Made No-GIL Pay Off

1In-Process Python UDF

Move Python UDF execution into the chDB process — no subprocess, no IPC.

Run UDFs inside the vectorized pipeline, called from worker threads in parallel.

Decorator: @chdb.func

2Module GIL-Independent

Declare extension Py_MOD_GIL_NOT_USED — opt out of the auto-GIL fallback.

Audit every piece of global state. Replace plain globals with thread-safe equivalents (atomics, per-thread storage).

Result: parallel SQL streams

3Low-Level Unicode APIs

High-level PyUnicode_AsUTF8 needs the GIL. On hot string paths it serializes everything.

Read PEP 393 internals directly: kind (Latin-1 / UCS-2 / UCS-4), data pointer, length — convert in C++.

15x faster on string-heavy queries

Trade-off: had to step outside the stable ABI — the limited API was no longer compatible with our performance goals.

What Broke. What Scaled.

Did not scale as expected

  • Naive PyObject_* calls in hot loops — refcount contention dominates
  • Shared Python objects across threads — biased reference counting hits its slow path
  • Stable ABI shims block direct memory access to PyUnicode
  • GIL "released" via context manager, but a single forgotten Py_INCREF re-serializes all threads

What actually paid off

  • Batching all Python access into one prepare phase, then pure C++ work
  • Direct memory layout reads — no Python C API on the hot path
  • Per-thread arenas for intermediate results — zero shared mutable state
  • Real wins on analytical workloads on a 16-core machine: parallel UDFs, parallel string processing

No-GIL is not a flag. It's an audit.

Practical Checklist for Porting Extensions

  • Build against the 3.14t free-threaded interpreter; flip Py_MOD_GIL_NOT_USED only after the audit, not before.
  • Grep your codebase for global mutable state. Wrap with atomics, mutexes, or move to per-thread storage.
  • Profile under contention — not just throughput. Refcount cache lines bounce; you'll see it as scaling cliffs, not crashes.
  • On hot paths, replace high-level CPython string APIs with direct PEP 393 access (kind + data pointer).
  • Batch Python interactions into a prepare phase; release the GIL once, then run pure C++ work in parallel.
  • Decide early whether to leave the stable ABI — performance-critical extensions usually have to.
  • Benchmark with realistic core counts (8, 16, 32). Single-thread numbers will lie to you.

No ClickHouse knowledge required — the same pattern applies to any Python C/C++ extension.
